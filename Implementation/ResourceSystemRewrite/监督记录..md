### 实际主流程与已落实部分

公开加载入口先检查可用状态，再路由、解析；串行提交内等待当前卸载记录、复用产物、加入同键记录或建立记录；新记录让出执行权、取得来源额度、提交批准后调用后端。产物提交关闭准入，逐个分配持有，再通知成功者；无人接收时清理，最后终结摘表并归还额度。业务卸载在提交外执行选择器，回到提交内复查该具体记录的持有，再启动释放。

已看到以下实际改动，但不以静态结构代替行为验收：

- 接续结果已在 `_AcquireAsync` 回到解析循环，`ResourceRecord.Complete` 按归属者和双失败策略通知；不重开已定的方案 A。
- 加载入口有 `TryGetUnloading -> RemovalTask`；池用 `AcquireResolvedAsync` 传入已选描述。普通加载重新解析、池保持版本仍需对应入口测试。
- `_Deliver` 关闭准入且先为成功接收者建立持有，再批量 `Deliver`；完成通知使用异步续体。原设计清单“成功提交后继续加入旧等待者集合”的字面缺口已有处理方向，剩余缓存命中和无人接收问题分别记 SUP-01、SUP-05。
- 转换契约已恢复 `conversionKey`。本轮只确认签名，未验收 Local/Remote 的身份与参数全链路。
- 设计采用的策略、外观、适配器职责有现成落点，不要求增加第 4 个模式，也不以核心文件数量证明可读性。

### 已确认缺陷与修复中事项

#### SUP-01 / 原 P1 / 已关闭（20:03）：缓存命中建立持有后不完成调用

- **触发**：一次加载已成功，随后再请求同键已有产物。
- **原代码证据**：19:56 版[缓存命中](D:/Workspace/Porjects/GameToolKit/Unity/Assets/ToolKit/Tools/Common/ResourceSystem/Core/ResourcePipeline.cs:201) 创建 `Waiter<T>.Granted`，建立引用却未完成 `Completion`，随后仍统一等待；命中分支没有 `record`，取消注册还会使用空记录。
- **原影响**：调用悬挂，已增加的持有无人归还；单独补一个完成通知仍未解释无记录分支的取消处理。
- **最小修复方向**：命中后直接返回在串行提交中已分配的引用，或明确实现不依赖加载记录的完成路径；不为命中另造加载生命周期。
- **关闭核查**：新版 237 行 `if (record == null) return waiter.DeliveredReference!`，直接返回提交内创建的引用，不再进入无记录等待和取消注册；分配仍由 `CreateHold` 完成，返回路径没有交付后的取消检查。主笔同时修正域外 Value 测试误用，监督重新运行现有“产物闲置后可复用且不再调用后端”用例，**1 通过、0 失败**，实际到达第二次加载并确认后端仅一次。关闭缓存命中悬挂本身；通用计数并发与交付边界仍由 SUP-02、SUP-03、V-01 独立跟踪，不扩大本项通过范围。

#### SUP-02 / P1 / 修复中，未关闭：取消、放弃与唯一执行未形成同一流程

- **触发**：后端暂停时个人取消；额度已被其他键占满时排队项全取消；最后等待者取消与新同键请求交错；请求超时。
- **代码证据**：运行前版本 `_AwaitWaiterAsync` 只等通知，没有令牌注册。本轮测试中主动取消、排队取消、超时均等到测试外层 5 秒超时。19:56 版本已补 255 行令牌注册和 280 行 `_CancelWaiterAsync`，不再把“没有注册”写成当前状态。但移除最后等待者与关闭准入分属 283、300 行两次提交；两者之间新请求仍可加入。304 行遇到未启动记录又调用一次 `_RunLoadAsync`，原来由 240 行启动的额度等待仍存在。267 行 Canceled 分支先抛取消，271 行的 `TimedOut` 判定不能处理 `Cancel(true)`。
- **影响**：新接收者可能被上一轮取消放弃；排队取消记录出现两个执行/终结者且不取消原额度等待；超时仍以主动取消结束。仅补令牌注册尚不足以关闭独立取消、额度及同键协调问题。
- **最小修复方向**：移除最后接收者和关闭准入在同一次状态提交中确定，提交外请求后端取消；保留原执行者负责真实结束与收尾，不再启动第二次执行；按实际取消来源报告超时。已交付结果保持归属调用者。
- **关闭条件**：A 取消立即结束且 B 继续；已取消归属者的失败不转嫁；全取消后 D 只等旧轮真实结束，再自己加载；排队全取消不启动后端、不阻塞后续额度，记录仅终结一次；超时保持既定诊断；交付完成后取消仍取得引用。使用受控提交边界覆盖同步完成与异步完成，不靠延时猜测。
- **20:03 定点更新**：Canceled 分支已补 `TimedOut` 检查，不再把其缺失列为当前代码事实；未专项复测超时。两次提交之间的准入窗口、未启动时重复 `_RunLoadAsync` 仍在，因此本项不关闭。

#### SUP-03 / P1 / 修复中，未关闭：独立持有计数仍未统一进入串行域

- **触发**：`Retain` 与另一个引用归还交错；默认 `ImmediateExecutionContext` 下不同线程同时归还各自凭证。

- **最小修复方向**：复用现有执行上下文，保证取得和归还持有实际串行；绑定线程的同步入口按已有线程契约检查，不增加同步阻塞桥或第二套计数。
- **关闭条件**：合法上下文内追加两份独立持有并逐份归还；默认上下文多线程归还计数准确；绑定线程误用按契约拒绝；尚有任意有效凭证时业务卸载不得释放。最新改动未取得这些验证证据。

#### SUP-04 / P1 / 未关闭：凭证失效与产物存活检查被总持有数替代

- **触发**：A、B 持有同一产物，A 已 Dispose 后读取 A.Value；或产物被外部销毁、管理器已释放而引用尚未归还。
- **代码证据**：[Value / IsValid](D:/Workspace/Porjects/GameToolKit/Unity/Assets/ToolKit/Tools/Common/ResourceSystem/Core/ResourceRef.cs:67) 的 Value 仅检查总 `HoldCount`，不检查 A 自身 `_disposed`、产物存活或管理器退出；IsValid 仅检查自身标志与总持有，没有既定的存活及上下文检查。与最终文档 §6、§10.2 不符。
- **影响**：已归还的凭证仍能取值，已销毁的对象仍可能被报告有效。其他引用的存在不能使 A 重新有效。
- **最小修复方向**：恢复凭证自身状态、所属产物/管理器有效性与线程契约的检查；撤下复用索引不应使仍合法持有的旧对象凭证无条件失效。
- **关闭条件**：A 归还后拒绝取值而 B 正常；外部销毁、管理器退出后失效；存活查询在线程边界内执行；同键新旧对象仍按具体对象身份独立持有。

#### SUP-05 / P1 / 未关闭：无人接收产物没有撤下实际复用索引和记录

- **触发**：所有接收者类型均不兼容，产物开始异步释放；释放未结束时到达新同键请求。无需先修复取消即可触发。
- **代码证据**：[无人接收分支](D:/Workspace/Porjects/GameToolKit/Unity/Assets/ToolKit/Tools/Common/ResourceSystem/Core/ResourcePipeline.cs:414) 只调用 `entry.Detach()`，它仅改 `_registered`；`ResourceStore.TryGetLive` 54 行仍从 `_current` 取对象且不看该标志。终结 454 行也未从 `_entries` 移除已清理记录。加载入口先查产物，再查已关闭的在途记录。
- **影响**：新请求能为待释放产物增加持有并绕过旧轮收尾；清理后容器还留有已释放对象，后续可能重复释放或再次复用。
- **最小修复方向**：通过容器撤下实际复用索引，原记录继续承担清理；清理成功或残留移交后移除该具体产物记录，再终结同键协调。
- **关闭条件**：暂停释放时新请求不得取得旧产物或提前启动同键后端；释放结束/残留移交后可继续，旧产物仅释放一次，不留下复用项和容器残项。

#### SUP-06 / P1 / 未关闭：撤下复用索引的旧产物无法被业务卸载

- **触发**：产物失效后被撤下复用索引，同键新产物已加载，旧引用后来归还，再调用业务卸载。
- **代码证据**：[SnapshotForSelection](D:/Workspace/Porjects/GameToolKit/Unity/Assets/ToolKit/Tools/Common/ResourceSystem/Core/ResourceStore.cs:84) 只遍历 `_current.Values`；旧具体产物留在 `_entries`。流水线 478 行只从该快照取得卸载候选。
- **影响**：旧产物虽然仍由容器拥有，却永久不在运行期业务选择范围中，只能拖到管理器退出处理。
- **最小修复方向**：业务卸载候选来自仍被系统持有的具体产物集合；复用索引仅决定加载命中。继续按对象身份复查与移除，保留同键新旧共存。
- **关闭条件**：旧产物最后一份引用归还后可被业务选中并释放；仍在使用的新同键产物不受影响；不由后续加载触发旧产物释放。

#### SUP-07 / P1 / 未关闭：失败残留没有完整交给独立脏集合

- **触发**：加载器/转换器抛出带 `CleanupRemainders` 的异常，未返回 LoadedAsset；或业务卸载释放失败，尤其调用者已取消等待。
- **代码证据**：[加载异常处理](D:/Workspace/Porjects/GameToolKit/Unity/Assets/ToolKit/Tools/Common/ResourceSystem/Core/ResourcePipeline.cs:372) 只保存 `.Error`，丢弃异常上的残留对象列表；`product == null` 时不进入产物清理。[卸载异常处理](D:/Workspace/Porjects/GameToolKit/Unity/Assets/ToolKit/Tools/Common/ResourceSystem/Core/ResourcePipeline.cs:524) 只把残留放入本次局部 `failures`，未加入 `_dirtyResources`，随后移除产物。只有 `_CleanupAsync` 的失败路径加入全局脏集合，且写入未遵守读取端使用的锁/同一串行域。
- **影响**：加载中间残留失去框架持有；普通卸载失败在快照中不可见，取消等待后也没有稳定结果接收者。并发清理对 List 的写入还缺少统一保护。
- **最小修复方向**：沿现有失败路径将实际残留一次性交给同一脏集合，业务结果可引用该记录；移交、容器移除与终结遵循已有串行边界，不增加按 key 封锁或自动重试。
- **关闭条件**：加载失败残留、普通卸载失败、取消等待后的迟到释放失败都能按对象身份在脏集合中找到；同键新加载可成功；没有重复释放、丢对象或并发集合损坏。
