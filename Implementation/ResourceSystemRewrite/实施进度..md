## 阶段 2：加载 → 合并 → 交付 → 归还 → 卸载（已完成）

### 完成的行为

1. **一条流水线**：`LoadAsync` 解析 → 等待"已放弃/正在卸载"的旧记录 → 复用命中 → 合并到在途记录或新建记录 → 等本轮结果。同一个文件内可读完主流程。
2. **成功交付与终结摘表合并为一次串行提交**（复核清单 #1）：关闭准入 → 登记产物 → 逐个建立独立持有 → 完成通知 → 终结 → 摘表，中间没有 `await`，没有新请求的准入窗口。
3. **接续尝试落到等待结果分支**（复核清单 #2）：通知结果为"本轮无产物"且本请求不是本轮归属者时，回到 `while(true)` 重新解析；归属者按失败策略判定，实现"每个请求最多承担一次失败"。
4. **卸载中途的等待分支**（复核清单 #3）：新增 `ResourceStore.TryGetUnloading`；命中正在释放的当前记录时等待 `RemovalTask` 结束后重新判定。池侧继续用 `AcquireResolvedAsync` 保留已选定原型版本。
5. **转换差异参数保留**（复核清单 #4）：`IFileResourceConverter.ConvertAsync(path, resultType, conversionKey, ct)`，本地/远端都把 `conversionKey` 纳入 `LocalKey`。
6. **排队取消不调用后端、不占额度**（设计 §3.1）：取到额度后**在串行提交内复查**"未放弃 + 仍有接收者 + 管理器未退出"才批准启动；等待失败不 `Release`，取得成功恰好 `Release` 一次。
7. **执行边界**：登记结束 → `await Task.Yield()` 显式让出 → 才调用加载器；弱契约有测试（后端第一行不在登记栈内，调用者先返回）。
8. **收尾契约**：`_CleanupAsync` 永不向上抛，可预期失败与清理崩溃同路返回错误；清理后仍在**同一次提交**内完成"移交残留 + 终结 + 摘表"。
9. **归还语义**：`ResourceRef<T>.Dispose()` 幂等、可任意线程；跨线程归还投递回串行域，不阻塞调用者线程；`Retain()` 追加一份真实持有。
10. **业务卸载**：`UnloadUnusedAsync(select)` 先取快照、在提交之外执行选择器、执行前以该记录**当前持有**复查；释放失败只产生一条脏记录，不阻止其他项。
11. **退出**：先通知等待者，再释放已登记产物；不以业务引用归零为条件。
12. **单个请求超时**：`RequestOptions.Timeout` / `ResourceSystemOptions.RequestTimeout` 只结束本请求等待，不取消共享后端，报 `RequestTimeout` 诊断码。

### 本阶段发现并修掉的实现缺陷（都属于"流程不成立"，不是风格问题）

| 现象 | 根因 | 修复 |
|---|---|---|
| 复用命中时 `NullReferenceException` | 命中分支把 `record` 留成 `null`，仍走 `_AwaitWaiterAsync` | 命中即返回已建立的持有；`_AwaitWaiterAsync` 只接受真实记录 |
| 等待侧取消完全不生效（取消后新请求永久等待） | 没有把调用者令牌登记为"交付前取消"，等待者永远留在接收者集合里 | 新增 `_CancelWaiterAsync`：移出接收者 → 取消该等待 → 无人时放弃记录（未开始则终结，已开始则取消后端） |
| 超时被当成主动取消 | 先 `ThrowIfCancellationRequested` 再判别超时 | 先判 `TimedOut` 报 `RequestTimeout`，再按主动取消 |
| 交付完成的等待者被取消回调改写成 Canceled，调用者拿不到已分配的引用 | `Cancel` 覆盖已置位的终态；且 `WaitResult` 默认值恰是 `Granted`，无法区分"未置位" | `WaitResult` 增加 `Unset`；`Cancel` 只在 `Unset` 时置位，已授予/已终结的终态不再改动 |
| `Retain()` 不增加持有 | 旧实现只新建凭证对象，没记持有 | `TryRetain()` 真实加一份持有 |

## 阶段 4：实例池（已完成，含一次结构自我修正）

### 完成的行为

- 池桶 = 原型引用 + **实例台账** + 等待者 FIFO；池键 = 原型身份 + 工厂 + 实例表示标识。
- 原型由资源流程按身份取得并**由桶持有到关闭**：闲置不释放，桶关闭才归还；等待旧记录结束时继续用已选定版本。
- **闲置优先复用**：归还的实例先交付给最早的等待者，配额已满时不再创建新实例。
- 每桶同时最多一次创建；等待者 FIFO；活跃配额 = 台账中在用实例数 + 创建中。
- 归还始终投递回串行域；重复归还只生效一次（以台账中的实例身份判定）。
- 原型不得提前归还：有闲置、在用实例，或创建/销毁进行中时都不关闭桶。
- 闲置上限 `MaxIdlePerResource`（含 0 = 归还即销毁）、闲置寿命 `IdleLifetime`、活跃配额 `MaxActivePerResource`；空桶到期（`Tick` 或桶自行到期）关闭并归还原型。
- 取消后的迟到实例按合法销毁流程处理；排队取消只结束个人等待，不取消已经开始的实际创建。
- 创建/销毁都观察到真实结束；销毁失败只影响该实例。
- `ClearPoolAsync` 关闭对应桶并销毁闲置实例；`InstanceLease<T>` 与引用凭证同构（`Value` 域内访问、`IsValid` 纯查询、幂等归还）。

### 本轮结构决定（一次自我修正）

- 初版把 `Active` / `Preparing` / `Creating` 做成独立计数器，实测发现**计数会与真实实例集合漂移**（归还、销毁失败、取消迟到实例各自增减）。已改为：**实例台账是"哪些实例存在"的唯一事实**，`ActiveCount`/`IdleCount` 从台账投影，另设 `InstanceLifecycle`（Active/Idle/Gone）。
- 与设计 §11.1"池的四个并行计数是保证的载体"不冲突：配额与"原型不得提前归还"的判据都还在，只是不再各存一份可漂移的计数。

### 实际验证结果

- 覆盖：首次租用加载原型并创建一次；归还后闲置再租用复用同一实例且不重复加载原型（`ReturnReset` + `RentReset` 都发生）；闲置上限为 0 时归还即销毁；活跃配额限制同时在用实例数（归还的实例被复用而非再创建）；每桶同时只创建一次且等待者按先来后到（实测 `peakConcurrent == 1`）；排队取消不创建实例也不占配额；存活查询异常不等于确认销毁且不产生销毁调用；清池销毁闲置实例并在下次租用时重新加载原型；未注册工厂诊断码；`CanCreate` 为假诊断码且不创建；创建失败只影响本次租用且可重试；闲置期满（假时钟 + `Tick`）实例被销毁且桶关闭；租约重复归还只生效一次。

### 本轮发现并修掉的实现缺陷

| 现象 | 根因 | 修复 |
|---|---|---|
| 存活查询异常直接抛到调用者线程 | `_ReturnCore` 直接调用 `Factory.IsAlive`，没有隔离 | `_IsReusable`：异常返回"不可复用"，撤销台账但不额外计一次销毁 |
| 返回闲置后不推进等待者，配额为 1 时又创建一次 | `_Pump` 只看创建，不看闲置 | `PumpResult`：闲置优先复用（`_ReuseIdleAsync`），否则创建 |
| `MaxIdlePerResource = 0` 时归还实例没被销毁 | 走了"取一个闲置实例销毁"，但该实例根本没进闲置集合 | 超上限的归还实例直接置台账 `Gone` 并调用销毁 |
| 归还路径把台账对象当成实例交付 | `PumpResult.Reuse` 传了 `TrackedInstance` 而非 `Instance` | 传 `idle.Instance` |
| `CanCreate` / `CreateAsync` 在串行域外读取原型值 | `PrototypeValue` 是引擎调用，与凭证访问约束同源 | 两处都经 `Context.Invoke` 在串行域内取值 |

## 阶段 2 补充（第二轮）：复核清单收口 + 一轮并发缺陷排查（2026-10-14 晚）

### 本阶段最重要的一次修复：本轮接收者名册

**现象**：`Continue` 策略下，归属者失败或取消后，**后继请求偶发永久悬挂**（首次实测为 5s/20s 超时）；有时表现为实际加载次数超过请求个数。

**根因（用内存轨迹逐条读出，非猜测）**：一次加载有两份"接收者"事实——批准启动时固定的名册 `Participants` 与可随时加入的 `_waiters`。三处各自取用其中一份：

1. `ApproveStart` 用 `_waiters` 组成名册并选出归属者；
2. `_Deliver` 之前用的是**当时**的 `_waiters`；
3. `Complete`（失败/终结提交）用的是 `Participants`。

在 2 与 3 之间加入的接收者会落进缝隙：既没进入本轮名册、又已经从 `_waiters` 被取走，**永远不会收到终态**，调用者永久等待。取消路径（`_CancelWaiterAsync` 移出接收者、`_AbandonAsync` 放弃记录）会让这个缝隙更容易命中。

**修复**：把"本轮要通知谁"收敛成**一次取走的名册**（`TakeRoster`）：

- `TakeRoster` = 批准启动时的名册 ∪ 取走时刻仍在等待的接收者，取走后清空 `_waiters` 并清空 `Participants`；
- 交付提交与终结提交都走同一份名册，因此**每个加入者恰好被结算一次**；
- 名册取走之后加入的接收者属于下一轮，下一轮的 `ApproveStart` 会重新组册；
- `Attach` 在记录已放弃或已终结时返回 `null`，调用方改为"等它结束收尾后重新解析"，不再挂到一个不会再通知任何人的记录上。

附带修掉的两个同源问题：

- **时间预算只结束本请求**：原先超时回调会走到"放弃记录 → 取消后端"，把**共享**后端取消掉，并用同一个令牌影响同一轮的其他请求（实测第二个请求被一起取消）。现在超时只移出该接收者、种自己的超时终态；只有调用者主动取消并导致本轮无人接收时才取消后端。
- **协商额度取得后才复查**：`WaitAsync` 期间被取消/放弃的记录，取到额度后在串行提交内复查不批准，归还额度且不触碰后端。

### 新增用例

| 用例 | 覆盖的保证 |
|---|---|
| 无人接收的迟到产物由原记录收尾且不留下复用项 | 退出通知等待者之后，**无视取消的迟到产物仍被原记录释放** |
| 后端返回失效产物时收尾释放且同键可以重新加载 | 失效产物不交付、被收尾释放、不留在复用索引；码 `LoaderInvalidResult` |

### 预加载的使用契约（设计 §7.1 要求写明，现在补上）

`ResourceManager` **不提供** `PreloadAsync`，预加载复用 `LoadAsync`：

- **只预热缓存**：`LoadAsync` 成功后立即 `Dispose()`。产物留在复用索引里，持有归零、进入闲置，后续同键请求直接命中，不再调用后端。
- **要求保留到使用时**：持有引用直到交接，交接后 `Dispose()`。
- **必须写进接入文档的误用警告**：**fire-and-forget 地丢弃引用**（既不 `Dispose` 也不保存）会让该记录持有数永不归零，`HoldCount != 0`，于是**永远不会被 `UnloadUnusedAsync` 选中**，成为不可回收项。这不是功能缺失，是一条使用约束。
- **能力边界**：`ResourceRow` 只有 `Key / State / HoldCount / WaitingCount`，**没有字节数、没有年龄**。所以需求第 5 条的"清理多少"只能表达为**按身份选择**（按来源、按 key 前缀、按是否有人持有），**不能按容量表达**；实施与文档都不得声称支持按容量清理。

## 阶段 8：对《监督记录》《验收报告》的逐项处理（2026-10-14 深夜～10-15）

> 两条清单已经写入内容（此前我记录的"0 字节"是过时事实，已在本文件更正）。**验收结论为不通过**：3 项运行时复现 P1 + 11 项静态确认 + 文件层 3 项 + 池层 3 项未关闭，另有测试债 V-01 与两处文档/注释与代码不符。

### 已修复

#### SUP-05（P1，GLM 运行时复现）：无人接收的产物释放后仍留在复用索引
- **根因**：无人接收分支只 `entry.Detach()`（仅清登记标志），而真正决定命中的是 `_current`；`_Terminate` 也不从登记集合移除。
- **修复位置**：`ResourcePipeline._CleanupAsync` 现在在释放完成（或残留移交）之后调用 `_RemoveProduct`，**撤下复用索引并结束具体条目的登记**；`_Terminate` 通过 `CleanupResult.EntryRemoved` 得知条目已收口，不再对它重复接管。
- **顺带修掉**：`product.Value` 原先在串行域外读取（引擎调用），改为 `_RetainedProduct` 经 `_context.Invoke` 在域内取；取不到时以记录本身作为残留线索，保证不回退成"丢对象"。
- **验证方法**：`dotnet test --filter "FullyQualifiedName~资源"`；关键用例《后端返回失效产物时收尾释放且同键可以重新加载》断言 `ResourceRows` 为空且同键能重新加载。GLM 报告 §3.1 P1 的复现步骤现在应观察到"新请求触发后端重新加载"而不是领到已释放对象。

#### SUP-09（P1，GLM 运行时复现）：业务卸载未完成时退出，同一产物被释放两次
- **根因**：`DisposeAsync` 忽略 `TryBeginUnload` 的返回值，对全部条目无条件再启动一次 `_RunUnloadAsync`。
- **修复位置**：`_RunUnloadAsync` 增加 `claimed` 语义——**释放责任只由取得成功的一方持有**；`DisposeAsync` 只在 `TryBeginUnload(force: true)` 成功时启动释放，否则改为等待该条目已有的完成通知。
- **验证方法**：用例《退出时释放已登记产物并使新请求失败》《主动卸载只释放无人持有的产物并返回计数》配合 FakeLoader 的释放计数。GLM 的"释放回调内阻塞 + Dispose"探针现在应观察到 `ReleaseAsync` 启动次数 = 1。

#### 新发现并修复：释放责任与启动之间的双提交缝隙（本次排查中暴露）
- **现象**：`UnloadUnusedAsync` 先在提交内 `TryBeginUnload`、再在提交外 `foreach` 启动释放；两者之间若有第二次调用进入，会看到"已标记释放中"，于是走"等待完成通知"分支，而**没有任何人启动释放** → 永久悬挂（实测 3 项卸载用例超时）。
- **修复位置**：`UnloadUnusedAsync` 把"取得责任"与"启动释放"放进**同一次串行提交**（`claimed: true`），已在他处释放中的条目改为等待其 `RemovalTask`；`TryBeginUnload` 的参数由 `ignoreReferences` 改为语义明确的 `force`。
- **验证方法**：卸载类用例连续复跑；该项与 SUP-09 同源，属于"至多启动一次"契约的实现细节。
