## 第 1 轮 【大肥鱼】2026-10-14 15:20

先说结论，我的意见是：**不要在这套骨架上继续做第三轮"删减迭代"，按需求重新定主流程，然后重做。**理由不是"代码丑"，而是它的复杂度分布在错误的位置——测试全绿、文档自洽，用户却读不出流程（D09 已经记过一次同样的事）。

### 一、先立三把尺子，后面所有争论都用它量

需求文件里只有一句话是硬指标：**"除开定义代码，核心流程代码不超过 10 份"**。其余都是功能项。所以我建议把验收改成三条，且顺序不能反：

1. **需求符合性**：需求文件 9 条 + 定位（跨项目、4 类来源）逐条兑现。
2. **可读性（本次第一优先级）**：一个没参与过的人，从 `ResourceManager.LoadAsync` 出发，能在 **10 个文件内**、**不靠 bool 标志组合**、**不需要先读文档**读出这条线：解析身份 → 命中复用或合并等待 → 谁执行一次加载 → 怎么交付 → 怎么归还 → 谁在什么条件下释放。
3. **行为正确性**：现有回归保留（214 个用例是资产，不是包袱），但它是必要条件，不是设计质量的证明。

**第 2 条现在是失败的**，这不是感觉问题。证据（都在现行实现里，不是历史）：

- 一条 `LoadAsync` 成功路径要穿 `ResourceManager → LoadManager._AcquireReferenceAsync → LoadOperation → PendingResourceRequest<T> → LoaderQueue → LoadManager._ConsumeLoadAsync → _RunLoadAsync → _NotifyLoadSuccess → ResourceStore.CreateReference → ResourceRef`，约 10 个自定义类型，其中 4 个是"为了这次调用临时造出来、完成即销毁"的在途对象。读者必须同时理解它们才能知道一次请求怎么走完。
- 一次请求的结局被摊在多个标志上：`LoadOperation.HasStarted / IsAbandoned / IsCleaningUp / Finished`，加 `PendingResourceRequest` 的四种完成方式（`CompleteWithResource / Fail / Retry / Cancel`），加 `ResourceState` 的 6 个值（其中 `Loading / Draining` 只是临时任务的**诊断投影**，不是容器的真实状态），加 `LoaderQueue._stopped`。判断"这次请求现在怎么样"要先看组合，这正是 D04。
- `LoadManager` 一个类同时干 6 件事：路由、同键合并、消费编排、产物交付、脏残留记录、业务卸载、退出。736 行。`InstancePool` 915 行。这两个文件加起来，核心流程已经不是"10 份"，是"20+ 份"。

### 二、复杂度花在哪了（我的判断，欢迎 GPT 反驳）

**① 三个正交的关注点被编进了同一条主线。**身份与合并（按 key 只加载一次）、并发执行（谁来跑、跑几个）、产物所有权（谁持有、何时释放）。三者本来可以各用一层、各用一句话讲清；现在是互相嵌套的：合并逻辑里要判断操作是否已放弃，消费循环里要复查请求取消，交付逻辑里要判断是否还有人接收。这就是"移动方法、改名、加 Manager 之后主线依然难追"的原因（D04 后半句）。

**② 在途记录被过度对象化。**`LoadOperation` 是"请求 + 接收者列表 + 取消源 + 完成信号 + 开始/放弃/收尾标志 + 进度分发器"的合体；`PendingResourceRequest<T>` 又是一层只为了把"我要的是 T"带进完成通知的抽象基类。这两个对象的生命周期只有一次加载那么长，却承担了 10 个可观察状态。

**③ 元数据比流程重。**诊断要 `LoadError` + `DiagnosticCode` + `LoadStage` + `CleanupStatus` + `RelatedErrors` + `CleanupRemainders` + `IErrorMapper` + `UserErrorCode` + `ResourceLoadException`，而且用户码映射在**三个**边界上各做一次（入口 catch、失败通知、取消分类）。需求第 9 条只要求"合理通知"，不要求两级错误码体系。

**④ 配置的暴露面大于实际作用面。**`LoaderPolicy.MaxConcurrentLoads = 0` 的语义是"一个分发循环且不限并发"——一个数字同时表达两件事；`PoolPolicy` 三个字段分属数量/时间/配额三种不同作用范围。这正是 D08 的形状。

### 三、我认为必须让 GPT 一起拍板的 6 个问题

5. **失败语义**：`FailWaitingRequests / ContinueWaitingRequests` 这个每来源策略，是需求推导出来的，还是实现自己长出来的？需求第 9 条只写了"任何任务的失败/取消不影响剩余任务"——那恰恰是 `ContinueWaitingRequests`，也恰恰说明**失败只影响发起者**就够了，不需要一个枚举。（这条我怀疑可以直接删。）
6. **重做幅度**：是否接受**破坏性改动公共 API**？我的意见是接受：这套 API 目前只有本项目 Unity 宿主在用，没有外部发布契约，我们不为"兼容旧形状"付第二份复杂度（D03）。
