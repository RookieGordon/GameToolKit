**明确保留的保证**（删了就是削弱已承诺契约）：

*资源与所有权：*
1. 结果产生→交付期间的暂管：**先建立持有、再完成任务通知**；成功后发生的取消不丢弃已分配的引用。
2. 迟到 / 无人接收 / 无效产物由**原记录**释放后才退出，不留给下一次请求补救。
3. 失效产物只撤下复用索引、**不触发释放**；旧引用仍绑定原对象；**同键新旧产物可以共存**（`ResourceStore.cs:44-53`）。
4. 业务卸载的 `select` 可能在串行域外重入取资源，故**卸载前必须复查持有**（`HoldCount != 0` 跳过）。
5. 下载文件运行期不删、只做启动清理；**文件填充合并**（同一文件多目标类型）与内存合并是两件事。
6. AssetBundle 只加载不释放，包生命周期在业务侧。

*池与线程（独立审查指出草案漏掉的 6 项，全部保留）：*

7. **原型不得提前归还**：`Idle`/`Active` 非空，或 `Preparing`/`Returning`/`Creating`/`Destroying` 任一非零时都不能释放原型（`InstancePool.cs:93-97`）。
8. **归还必须始终投递回串行域**，不采用同上下文立即归还——因为 `InstanceAutoReturn.OnDestroy → lease.Dispose` 会在销毁回调里触发（`InstanceLease.cs:62`）。
9. **每桶同时最多一次创建 + 等待者 FIFO**（`InstancePool.cs` 建桶与 `Pump` 逻辑）。
10. **活跃配额 = `Active + Preparing + Creating`**（`InstancePool.cs:478-479`）。
11. **创建/销毁必须观察到真实结束**；取消后的迟到实例必须销毁或按合法归还流程处理。
12. **存活查询异常不等于确认对象已销毁。**

*错误身份：*

13. **保留 `DiagnosticCode` / `LoadStage` / `DiagnosticId` 一层不变**——独立核查确认约 21 个测试断言这些身份。**用户码映射层（`IErrorMapper` + `UserErrorCode`）也保留**——缺少足够的删除依据就不删除既有扩展能力；将来有新证据再评估。

## 3 主流程

一条流水线，四份契约，三个容器。四类来源共用同一条流水线。

```text
LoadAsync<T>(address, source, options, ct):
    repeat:
        key = 该来源加载器.Resolve(address).标识        // 落在产物容器命名空间内
        record = 在途表.Find(key)

        if record != null:
            if record.不接受新接收者:                    // 已被放弃：只等它结束，不要它的结果
                等待 record 结束
                continue
            等待者 = record.加入<T>(ct, options.Progress)
            // ★ 交付段在完成本等待者之前已经为它建立了独立持有，这里不再加持有
            return await 等待者.完成通知                  // 可能得到引用、失败，或"本轮无产物"

        if 产物容器.TryGet(key, out p) 且 p.存活:
            return p.加持有<T>()                        // 命中：不排队、不建记录，现场建立持有

        建记录 R → 在途表.Add(key, R)
        等待者 = R.加入<T>(ct, options.Progress)         // 首个接收者
        启动一次执行(R)                                  // 见 §3.1 边界规则
        return await 等待者.完成通知

执行一次(R):
    让出执行权                                  // 边界规则：外部代码不得嵌在登记栈内（§3.2）
    额度已取得 = false
    产物 = null; 失败 = null; 已交付 = false; 需收尾 = false
    try:
        await 并发额度(source).WaitAsync(R.取消源.Token)   // 令牌只负责"尽早退出"
        额度已取得 = true
        批准 = false
        在串行域内:                             // ★ 取到额度后必须在提交内复查（§3.1）
            批准 = R.接受新接收者 and R.等待者非空 and 管理器未退出
        if 批准:
            产物 = await 加载器.LoadAsync(R.键, R 进度转发, R.取消源.Token)

            在串行域内:                          // 提交阶段：只在这里改状态
                if R 已放弃 or 产物 无效:
                    需收尾 = true
                else:
                    产物容器.Add(R.键, 产物)
                    持有 = []
                    for 每个未取消的接收者 r:     // 类型不匹配 → 只该项失败，不得中断整个提交
                        try: 持有.Add((r, 产物.加持有(r.请求类型)))
                        catch: r.失败(类型不匹配)
                    已交付 = 持有.Count > 0
                    for (r, 引用) in 持有: r.完成(引用)   // ★ 先在上一行建立持有，这里只负责通知
                    需收尾 = !已交付
    catch e:
        失败 = e                                // 原始错误保留在 R 上
    finally:
        if 产物 != null and !已交付:
            需收尾 = true                       // ★ 提交阶段自身抛错（如用户工厂回调）也不能漏掉产物
        try:
            若需收尾:
                // ★ 收尾的签名契约：永不向上抛。
                //   可预期的释放失败 → 返回（残留, 原始错误）；
                //   不可预期异常（清理路径自身的 bug、清理期间观察到的取消等）→ 就地 catch-all，
                //   连同异常对象一起转成错误返回。清理失败与清理崩溃同路。
                //   理由：内层 try 只有 finally、没有 catch，"不向上抛"若只写在注释里，
                //   一旦抛出，下面的终结与摘表会整体跳过 —— 外层 finally 只保得住额度，保不住 key。
                残留, 收尾错误 = await 收尾(产物)
            在串行域内:                          // ★ 唯一终结与摘除点，成功/失败/拒绝共用
                // ★ 四步并成一次提交（之间没有 await）
                if 需收尾:
                    if 产物 已登记且无人接收: 产物容器.Remove(该记录)   // 不能留下指向已释放产物的复用项
                    移交残留（或把 收尾错误 + 残留 记入脏集合）
                R.终结(失败 ?? 收尾错误)           // 幂等：只种一个终态；一次性通知所有仍等待的请求
                在途表.Remove(R.键)               // ★ 摘表发生在本轮收尾完成之后，且与终结同一提交
        finally:
            额度已取得 → 并发额度(source).Release()  // ★ 外层 finally：提交与收尾的异常出口也覆盖
                                                     //   等待失败不 Release；取得成功恰好一次
```

> **一条主线，三个出口，全部走同一段 `finally`**（讨论中改了三次才收敛）：
>
> | 出口 | `产物` | 是否已交付 | 动作 |
> |---|---|---|---|
> | 拒绝启动 | null | 否 | **终结 → 摘表 → Release**（拒绝判定发生在 `WaitAsync` 成功之后，**额度必已取得**，所以确实会 Release） |
> | 无产物失败（含排队取消） | null | 否 | 通知失败 → 终结 → 摘表 |
> | 后端报错 | null | 否 | 同上 |
> | 交付成功 | 非 null | 是 | 终结 → 摘表（产物已被持有，收尾无事可做） |
> | 无人接收 / 已放弃 | 非 null | 否 | `await 收尾` → 移交残留 → 终结 → 摘表 |
>
> **不变式**：**每个出口都恰好做到——记录恰好终结一次、恰好摘表一次；额度要么从未取得、要么恰好 Release 一次。**
>
> **关于"摘表"的位置**：放在 `finally` 里没有问题，**真正的条件是"它发生之前本轮收尾已经完成"**。本实现把 `await 收尾` 也放进同一个 `finally`，因此摘表天然在收尾之后。**不要把它改回"finally 之后另起一段语句"**——那条语句在 `return` 与异常的出口上不会执行。

> **"收尾"必须把"永不向上抛"写进签名契约**（GLM 第 21 轮指出：这原本只活在注释里）：
> - **可预期的释放失败** → 返回 `(残留, 原始错误)`；
> - **不可预期异常**（清理路径自身的 bug、清理期间观察到的取消等）→ **就地 catch-all，连同异常对象一起转成错误返回**；
> - 于是**清理失败与清理崩溃同路**，尾部那次"终结 + 摘表"提交成为**不可跳过段**——只剩进程级致命故障在其外，与本文档其他保证同界。
>
> 若只写"不向上抛"而不落成结构，内层 `try` 只有 `finally` 没有 `catch`，一旦抛出，**终结与摘表整体跳过；外层 `finally` 只保得住额度，保不住 key**——"不永久封锁 key"就失效了。这里检查的仍是**清理**这一类，**不是**为假想 OOM 之类做无限容错。

> **本轮产物若已登记却无人接收，必须从可复用集合撤下**：否则容器里会留下一个**指向已释放产物**的缓存项，后续命中它就会交付一个已死对象。

> **"终结记录"与"允许下一轮"必须是同一个时刻。**
> 曾经的设计是"先终结记录的完成任务、之后才摘表"。那会让 D 在旧记录仍在收尾时就被唤醒：**重新解析 → 又找到同一条记录 → 又等那个已经完成的任务**，形成重复尝试，同步路径上还会占住执行线程。所以：**终结 = 摘表 + 完成信号，二者同时发生**。尚未通知的失败请求在收尾之后通知即可——**当前没有需求要求它们在收尾前就知道**。个人取消仍可立即结束自己的等待。

```text
归还有产物:
    Dispose: 记录.持有-- ；归零 → 记录进入"闲置"（只是记账，不卸载、不删文件）

UnloadUnusedAsync(select, ct):
    主线程: 选出 持有==0 且 select 命中的记录，标记"释放中"

    主线程: 移除该记录；返回 { 释放数, 跳过数, 失败列表 }
```

### 3.1 排队任务被取消后不得不调用后端、也不得占用并发额度

删掉每来源常驻队列后，这条保证改为**取到额度后再做一次串行提交判定**（不需要新字段）：

> ① **取并发额度用记录的操作令牌**：`await 并发额度.WaitAsync(R.取消源.Token)`——令牌只承担"尽早退出"，**不承担批准职责**。
> ② **取到额度后，在串行提交内复查"当前接收者 + 是否已放弃 + 管理器是否已退出"，再决定是否批准启动**。
> ③ **未批准 → 归还已取得的额度，且不调用后端。**

**为什么必须有 ②（讨论中纠正过一次）**：`WaitAsync` 成功取到额度**不会被后来的取消追溯撤销**。若等待者在"取到额度之后、进入后端之前"全部取消，只看令牌会照常调用后端——**既浪费一次后端工作，也占着额度**。"取到额度后仍有人等待"并非必然。

**④ 批准提交必须是后端第一行之前最后一次状态修改**，批准与后端调用之间不得插入任何用户回调——否则用户代码骑在"已批准"状态上执行，§3.2 的弱契约被绕过。

**⑤ 批准之后发生的取消一律按"执行中取消"处理**：令牌交给后端，产物迟到由本记录收尾（§4.5 路径），不再复查"还有没有人要"。

**⑥ 额度纪律**：等待失败不 `Release`；取得成功则所有出口恰好 `Release` 一次；未批准则归还已取得的额度并**不触碰后端**。

> **本节规则只在 §3 的主伪代码里实现一次，不再单独给代码块。**
> 讨论中曾出现同一函数两份代码并存（编辑残留）：旧版正是警告 1 明令禁止的形状，读者照哪份实施都"有文档依据"。**§3 的实现是唯一版本**，本节只讲规则与理由。

**验收（现有测试未覆盖，必须补）**：*排队中的记录被全部取消后，加载器调用次数不增加、且并发额度未被占用*——构造额度为 1 的加载器，先占满额度、再让排队项全部取消、然后放入一个有人等待的任务，观察它**不被取消项阻塞**。（现行 `ConsumerCancellationBoundaryTests.cs:71-98` 只覆盖"已开始后取消"。）

### 3.2 执行边界规则（第 2 轮讨论的结论，实测得出）
- **`await` 本身不是边界**。实测：`SemaphoreSlim.WaitAsync` 在额度空闲时同步完成，后端代码会在调用者栈上执行；同步完成的后端会让整段加载在调用者栈上跑完（`producer:return taskDone=True`）。
- **边界 = 状态登记已结束 + 显式让出执行权。** 必须显式让出，不能靠"写了 await"。
- 验收拆两条，不合并：
  1. **弱契约（必测）**：状态登记退出后才启动外部代码，后端第一行不嵌在状态修改栈内。
  2. **强契约（单独测，带线程前提）**：调用者返回时后端尚未开始。此条在 Unity 主线程同步上下文下不能由默认调度直接推出。
- 实测前提：无线程池同步上下文 + `ConfigureAwait(false)`。探针源码见 [取证-await边界探针.md](取证-await边界探针.md)。

### 4.2 记录必须活到"整个收尾完成"

> 调用者在途表里**查不到记录** ⟹ 这次加载的**整个收尾已经完成**（释放已完成，或清理失败的具体残留已经移交）；**查得到** ⟹ 收尾还没完成。

**两个必须写准的地方（讨论中纠正过两次）**：

1. **不是"后端与清理都未结束"**——后端可能已结束而清理仍在 await。准确说法是**记录尚未完成整个收尾**。
2. **不能因为释放失败就永久挡住这个 key**：残留移交后即视为收尾完成，记录照常移除。

**这要求记录移除必须发生在整个收尾完成之后。** 第 8 轮草案的伪代码把 `在途表.Remove` 与通知放进 `finally` 而**没有任何收尾动作**，D 会与未收尾的旧后端重叠——该草案已作废。

> **引理：`终结` 与 `摘表` 在同一次提交内发生，且这次提交发生在本轮收尾完成之后。**
> - **成功路径**：建立持有并通知 → `终结 + 摘表`（产物已有人持有，收尾无事可做）；
> - **失败 / 排队取消 / 拒绝启动**：通知 → `终结 + 摘表`；
> - **无人接收 / 已放弃 / 无效**：`await 收尾(产物)` → 移交残留 → **在同一个串行块内** `终结 + 摘表`。
>
> **特别注意第三步必须并成一次提交**：若把"移交残留"与"终结+摘表"写成两个串行块，中间会被其他提交插入，`查不到 ⟹ 整个收尾已完成`这句字面在缝隙里不成立。三步之间没有 `await`，天然可以并成一次提交。
>
> **实现只有一处**：§3 主流程的 `执行一次(R)`。本节只讲顺序规则，不再重复代码——同一函数两份代码并存会让读者照哪份实施都"有文档依据"。

**关于"全部等待者已取消时谁被通知"**：没有通知对象。记录的任务以"无产物"终结即可，`D` 等待的就是这个任务；**不需要为无人等待的情况发明第二个完成信号**。

### 4.3 等待侧规则：完成通知一旦置位即所有权交接

**交付后取消不会丢掉已分配的引用**——串行域使"取消提交"与"交付提交"全序：取消在前，接收者已被移出、"未取消"过滤跳过它、不为它建持有；取消在后，请求已完成，引用已归属调用者。

**但唯一泄漏窗口在等待侧管路**（GLM 第 17 轮指出）：若等待者用 `WhenAny` 式"令牌与完成通知赛跑"的等待，令牌在**交付提交之后、调用者恢复之前**触发，调用者会拿到 `OperationCanceledException`，而**引用躺在没人认领的已完成任务里**。所以必须写死：

> **完成通知一旦置位即所有权交接；个人取消此后不得短路该通知**，只能促使业务提前 `Dispose`。取消只驱动"交付前的取消提交"。

现行代码就是这个语义（`_CancelRequestAsync` 在 `_FinishLoad` 之后 `Remove` 失败即空转）。

**验收**：*交付提交完成后立即使某等待者令牌失效 → 该调用者仍取得有效引用；总持有数 = 交付数，全部 `Dispose` 后归零。*

### 4.4 记录还必须表达"是否接受新接收者"

**"普通合并"与"D 只等待、不接收"是两条不同路径，必须能区分**，所以记录上确实需要一个"还接不接受新接收者"的事实。

- 记载方式可以换（不必是原来的 `IsAbandoned` 字段形状），**但这个事实不能省**；
- 本文档**不承诺"删光相关状态"**——这类删除项在定稿前一律标为**候选**。

### 4.5 全部等待者取消后，新请求（D）怎么走

> **D 只等待旧记录结束，不接收它的任何结果。**旧记录的迟到产物由旧记录自己收尾；收尾完成后 D 重新解析、发起新的一轮。

理由：全取消时已向旧后端发出取消请求，其结果在语义上不属于任何人，交给 D 等于让 D 接收一份"为别人发起、已被放弃"的产物。准入条件按 §4.2 表述。

### 5.1 `ResourcePipeline` 为什么可以在一个文件里，以及理由要说准

**先说清两条不成立的旧理由**（我此前写过，均已在讨论中撤回）：

1. **"现行拆三处是 D05 的病根"** —— 不成立。**D05 记的病根是"所有权交接未定义"，不是文件数**；而 D04 的纠正方向是"容器保存记录、编排者推进流程"。拿 D05 当合并收益，是**用已修复的历史问题充当本次收益**。
2. **"三者共用同一份事实所以是一件事"** —— 不成立，**共同访问一份事实推不出它们是一个职责**。

**成立的依据只有一条**：**可以在一个文件里放"编排者及其内部记录/容器/凭证类型"，以满足文件边界；但各类型仍各守职责。** 文件边界与职责边界是两个层面，合并文件是为了让**读者在一个文件内读完一次加载的完整流程**，不是因为职责相同。

**判定标准不是"能不能放进一个文件"，而是"读者能否在一个文件内追完主流程，且各类型职责仍可单独说明"。**

### 6.1 扩展契约（四份，对应需求第 1、7 条与"可替换下载"）

**契约上的约束（现文档已有，方案保留）**：

- `ResolveAsync` **不交出需要框架释放的对象**——它只回答"这是什么"；`LoadAsync` 才交出所有权。这条是"身份解析与加载分开"的全部理由，也是池能固定原型版本的前提。
- `LoadedAsset.ReleaseAsync` 由框架**至多启动一次**；未提供释放回调的产物（如 AssetBundle 资产）表示所有权不在框架，框架不推断自己拥有其底层包。
- `Progress` 只在加载器会上报时才有意义；现行内置远端加载器不上报，进度能力为将来的加载器保留。
- 工厂的 `IsAlive` / `CanCreate` / `GetInstanceKey` 必须无副作用且不阻塞；`OnRent` / `OnReturn` 在串行域内同步完成。

### 7.1 两处口径更正（独立审查指出，避免表述拔高）

**① 预加载的两种用法与一条误用警告**：本方案不缺预加载能力，因为 `LoadAsync` 成功后产物留在产物容器里；但**持有归零只能靠 `Dispose()`**（现行 `ResourceStore.cs:116-128`），所以：

- **只预热缓存**：`LoadAsync` 成功后立即 `Dispose()` → 持有归零、进入闲置，后续调用直接命中。这就是预加载。
- **要求保留到使用时**：持有引用直到交接。
- **误用警告（必须写进接入文档）**：**fire-and-forget 地丢弃引用**（既不 `Dispose` 也不保存）会让持有**永不归零**，该记录 `HoldCount != 0`，**永远不会被 `UnloadUnusedAsync` 选中**，成为不可回收项。

> 说明：讨论中曾一度改判为"必须新增 `PreloadAsync`"，**该改判已撤回**——上述陷阱是一条必须写明的误用警告，不是"功能无法表达"的证明。

**② "清理多少"的能力边界**：`ResourceRow` 只有 `Key / State / HoldCount / WaitingCount`（`ResourceDiagnostics.cs:63-77`），**没有字节数、没有年龄**。所以需求第 5 条的"清理多少"在本方案中只能表达为**按身份选择**（按来源、按 key 前缀、按是否有人持有），**不能按容量表达**。这与 D08 记载的"框架不管理资源内存容量"一致，但把它写成"清多少都支持"属于拔高——**能力边界就写在这里，实施时不得声称支持按容量清理**。

## 10 线程与生命周期：三个必须说准的动作

**保留一个执行上下文（"状态串行域"），但理由收窄为下面三条可检验的行为**，不再声称它是唯一方案、也不以成员数量论优劣。

### 10.1 后台线程的幂等归还

```text
Dispose():
    一次性占用中断: 若不是第一个调用者 → 直接返回        // 幂等，不加锁
    已在串行域 → 就地释放这份持有
    否则 → 把"释放这份持有"投递到串行域，不等待、不阻塞
```

- **绝不在调用者线程上同步阻塞等主线程**，否则后台线程会卡住游戏帧。
- **禁止的是同步阻塞，不是 `await`**：加载结果登记、引用分配这类操作**需要可等待的提交**，确认完成后才向业务交付。所以不能概括为"全部跨线程交互都不等待"。
- 投递后引用对业务**立即失效**；实际记账稍后在串行域完成。**这个"已失效但尚未记账"的窗口必须写进文档**：业务在 `Dispose` 之后立刻调用 `UnloadUnusedAsync`，可能仍看到该项被持有而跳过——**这是可接受的保守方向**，不会提前释放在用资源。
- **运行期要求上下文接受归还投递**（主线程运行时这是常态）。**不能"投递失败只报诊断就算完成"**——凭证已失效而计数未归还，会**永久留下持有**，该项再也不会被 `UnloadUnusedAsync` 选中。退出期的处理沿现有进程退出清理边界说明即可，**不为它新造恢复体系**（D02）。
- 不为这个窗口发明"待归还队列"或"归还完成信号"：`UnloadUnusedAsync` 本来就是业务择时调用，不是同步点。

### 10.2 `Value` / `IsValid` 的线程约束

**恢复现行行为：只在串行域内访问，非串行域访问 fail fast（可诊断异常）。**

- 已在串行域（Unity 主线程）→ 就地求值，无额外代价。
- 其他线程 → **不做同步阻塞等待**（那会在主线程上卡顿甚至死锁），而是抛出可诊断异常；文档写明约束。
- 不用"缓存存活标志"绕过引擎调用——那会削弱现行语义。
- 第 3 轮曾主张放开为任意线程纯读，**已撤回两次**，此处为最终立场。

### 10.3 两类跨线程交互必须分开，且串行域不自动兑现 D07

**跨线程交互有两类，不能概括成一句**：

| 类别 | 动作 | 等待方式 |
|---|---|---|
| **登记 / 交付 / 引用分配** | 加载结果登记、为接收者建立持有、完成任务通知 | **可等待的提交**——确认完成后才向业务交付 |
| **归还** | `ResourceRef.Dispose` / `InstanceLease.Dispose` | **投递即走**，调用者不等待 |

**禁止的是同步阻塞，不是 `await`。**

- 跨线程交互**没有第三种形态**：不会同步阻塞等待主线程；串行域也不等待业务归还（D02）。
- **诚实说明代价**：串行上下文**同样可能同步重入**——用户回调若就在主线程上被调用，那就是嵌在状态提交里。**所以保留串行域并不自动兑现 D07**，必须靠"提交与外部调用分离"的纪律 + 验收断言，不能借"结构更可靠"掩盖。
- **真实代价是吞吐与帧耦合**：状态记账需与主线程交错，后台加载完成后的交付要排到主线程。这是可接受的（交付本来就要在主线程碰 Unity 对象），但必须写明。
- **测试实现"直通"不能在多线程测试里冒充串行**：验收需有一条"测试上下文必须真正串行"的检查。

## 12 采用的 GoF 模式（按已有职责选，不凑数）

**共 3 个，主模式 1 个、辅助 2 个。**

| 模式 | 在本设计中承担什么 | 解决的具体问题 | 与其他模式的关系 |
|---|---|---|---|
| **策略（主）** | `IResourceLoader`（一种来源一份实现）、`IInstanceFactory`、`IFileResourceConverter` 三处替换点；失败语义按来源配置也属策略选择 | 业务要替换加载实现与目标类型转换，且**框架不预设具体实现** | 是"外观"内部的执行体；"适配器"把具体平台实现接到它的契约上 |
| **外观（辅）** | `ResourceManager` 作为唯一业务入口，隐藏流水线、容器、池、串行域 | 业务只需 `LoadAsync` / `RentAsync` / `UnloadUnusedAsync`，不需要知道记录、等待者、额度 | 转发给"策略"的实例；不承担具体定位与加载算法 |
| **适配器（辅）** | 把 Unity 原生加载、第三方下载工具、业务工厂接到既有契约上（`ResourcesLoader`、`SimpleAssetBundleLoader`、`DownloadInvoker`） | 平台 API 与框架契约形状不同，且**平台行为不应渗入核心** | 实现"策略"的接口；位置在接入层 |

**同一条流水线上不引入第 4、5 个模式**：`LoadAsync` 的一次请求合并、额度批准、交付与收尾是**一条顺序流程**，用状态模式或责任链会把流程切碎——**这正是我们要脱离的旧结构**。
