## 0 一句话方案

**一条流水线，四份契约，三个容器。**

- 一条流水线：`按地址解析成键 → 键上有产物就加持有 → 没有就并入同键的在途任务 → 任务完成落到容器 → 交引用`。四类来源共用它。
- 四份契约：加载器、文件转换器、实例工厂、文件填充（下载）——正好对应需求第 1、7 条与"可替换下载"。
- 三个容器：产物容器（谁在用）、在途任务容器（同键只跑一次）、池容器（闲置实例）。

## 1 主流程（伪代码，就是最终要读出来的东西）

```text
LoadAsync<T>(address, source, options, ct):
    key = 该来源加载器.Resolve 后的标识
    在途 = 在途表.Find(key)

    if 在途 != null:
        return 并入在途.加一个接收者<T>(ct, options.Progress)

    if 产物容器.TryGet(key, out 产物) 且 产物.存活:
        return 产物.加持有<T>()                    // 命中：不排队、不建任务

    return 建任务(key, address, source, ct)         // 见下

建任务:
    任务 = { key, 接收者[我], 取消源 }
    在途表.Add(key, 任务)
    开始执行一次(任务)                              // fire-and-forget，见第 3 节
    return 任务.完成通知

执行一次(任务):                                    // 只执行一遍，所有接收者共看结果
    await 并发额度(source).WaitAsync(任务.取消源.Token)
    try:
        if 任务.接收者.全部已取消: return           // 没人要了，不碰后端
        产物 = await 加载器.LoadAsync(键, 进度转发, 任务.取消源.Token)
        if 产物 无效:
            return 任务.失败(产物无效)
        产物容器.Add(键, 产物)                       // 登记一份记录
        任务.一次性交付(产物)                        // 逐接收者: 加持有 / 已取消则跳过 / 类型不符则该项失败
        if 任务.无人接收: 产物容器.Remove(记录); await 产物.Release()
    catch e:
        任务.失败(e)                                // 接收者只失败一次；后到请求重新走 LoadAsync
    finally:
        在途表.Remove(任务.Key)                     // 后来者从这一刻起可以重新发起
        并发额度(source).Release()
```

`ResourceRef.Dispose` 那一步：

```text
Dispose:
    记录.持有--
    if 记录.持有 == 0: 记录 进入"闲置"                   // 只是记账；不卸载、不删文件
    幂等；可从任意线程调用（投递到主线程改计数）

UnloadUnusedAsync(select, ct):
    主线程: 选出 持有==0 且 select 命中的记录，标记"释放中"
    释放: await 记录.产物.Release()                     // 失败 → 一条脏记录，不影响别的
    主线程: remove 记录；返回 {释放数, 跳过数, 失败列表}
```

就这么多。**没有**：队列、消费者循环、信号量唤醒、放弃标志、收尾标志、进度代理对象、两级错误码、每来源失败策略、绑定代际。

## 3 执行模型：为什么可以不要常驻消费者

前提命题：**在第一个 `await` 之前不碰后端**，由 `执行一次` 的第一行就是 `await 并发额度.WaitAsync(...)` 保证（`SemaphoreSlim.WaitAsync` 绝不内联执行后续代码）。

于是常驻消费者现在提供的四件事，分别落到：

| 消费者现在给的 | 替代品 | 代价 |
|---|---|---|
| 后端不嵌在生产者的同步调用栈里 | `WaitAsync` 之后的续体 | 同步后端会主线程序列执行；这正是 Unity 原生加载要的 |
| 每来源并发上限 | 每来源一个 `SemaphoreSlim(LoaderPolicy.MaxConcurrentLoads)` | 无 |
| 排队中的任务不执行（全部取消就跳过） | 任务开头的"接收者全部已取消 → return" | 已是必要检查 |
| 消费者异常不污染生产者 | 任务自己 catch + 完成通知单终态 | 更简单 |

**剩下唯一的真差异**：现在的 FIFO 队列保证同来源任务按登记顺序**开始**；信号量只保证不超过 N 个同时跑，不保证顺序。要请 GPT 举反例：**有哪个真实流程需要"同来源按登记顺序开始"？** 我目前能想到的只有"AB 包内资产按序加载"——而那属于业务加载器内部的事（需求已写明 bundle 由业务层维护），不该由框架的队列代管。

## 4 线程模型候选：把 `IExecutionContext` 从流程里拿掉

规则改成两条，写进文档即可，不再需要一个抽象：

1. **所有接触框架状态的代码只在 Unity 主线程执行**：用 Unity 的 `SynchronizationContext` 恢复即可，锁、标志、投递全部不需要。
2. **只有两个操作允许来自其他线程**：`ResourceRef.Dispose` / `InstanceLease.Dispose` / `ResourceManager.Dispose`——它们是"投递到主线程的幂等请求"，实现里只有这几行出现调度词汇。

`ResourceRef.Value` 现在要求"在上下文内访问"（`AssertAccess`，否则抛异常）。候选改成：`Value` 是纯读、可从任意线程读引用到的对象，但**文档明确要求不得在任意线程调用 Unity API**——这条约束本来就由引擎决定，框架不必自己造一个断言层。请 GPT 判断这是"削弱保证"还是"删掉重复职责"。

## 6 保留清单（不能删，删了就是削弱已承诺的保证）

- 结果产生→交付期间的暂管：**先建立持有、再完成任务通知**，成功后取消不丢已分配的引用。
- 无人接收 / 无效产物 / 迟到产物：由**原任务**释放，不留给下一次请求补救。
- 旧产物失效只撤下复用索引，不触发释放；旧引用仍绑定旧对象（D05）。
- 业务卸载的 `select` 可能在状态提交外重入取资源 → **卸载前必须复查持有**。
- 下载文件运行期不删、启动按目标清理（D01 的边界）。
- 文件填充合并（同一文件多目标类型）与内存合并是两件事，不能互相替代。
- AssetBundle 只加载不释放，包生命周期在业务侧。
