## 1. 定位与边界

✅ **框架管什么**：来源注册与替换、身份解析、同资源共享一次加载、交付独立引用/租约、归还与业务选择卸载、实例池化、远程文件落盘与转换。

✅ **框架不管什么**（R02 及“不自动扩张的能力”）：AssetBundle 容器/依赖/清单/版本/下载/生命周期归业务，核心只对后端交出的 `LoadedAsset.ReleaseAsync` 负责；不内置 AB 加载器；不做内存硬配额、运行期磁盘硬配额、热更新、跨进程一致性。业务不提供释放回调时，框架不推断自己拥有底层对象。

🔶 **内置来源**：本地、远程、Unity Resources 由框架内置（Resources 实现在接入层 `ResourcesLoader` + `ResourcesInstanceFactory`）；AssetBundle 只内置契约。当前仓库**没有** Resources 实现，属本次交付缺口。

## 2. 角色职责（每句一件事）

| 角色 | 一句话职责 | 不做什么 |
| --- | --- | --- |
| 资源入口 | 组织加载流程与实例池，暴露取用、归还、卸载、退出 | 不创建缓存/加载器/工厂，不实现定位与加载算法 |
| 加载流程 | 解析身份、合并同一次加载、交付凭证、受理归还与按业务选择卸载 | 不拥有实例池，不读磁盘 |
| 一次操作（记录） | 保存本轮实际加载的事实、接收者与终态 | 不决定业务看到什么 |
| 具体产物（产物记录） | 保存对象与**唯一一份**释放责任 | 不调度加载，不自动淘汰 |
| 引用凭证 | 一个业务的一份持有，归还即失效 | 不改共享事实，不等待 |
| 实例池 | 维护闲置实例与实例对原型、工厂的依赖 | 不做资源定位与业务卸载 |
| 加载器 | 一种来源的定位与生产，交出可释放产物 | 不管共享、计数与等待者 |
| 文件缓存 | 本地内容的取得、发布、有效期与删除策略 | 不解释业务对象，不决定资源身份 |

## 3. 装配关系

✅ **核心接收依赖，便利装配放在接入层。**

- 项目创建缓存与后端；入口组织加载流程与实例池；**缓存谁创建谁关闭**。
- 只用 Unity Resources 的项目不创建磁盘缓存——现在 `ResourceManager:43,86` 无条件创建并等待 `FileCache.InitializeAsync`，缓存目录不可写会把整个资源入口的初始化拖失败。
- 入口**并列**组织加载流程与实例池（不再是流程拥有池）；池只依赖窄接口 `IPrototypeProvider`（提供“按已解析原型取得凭证”），不再回依赖流程的 `Context/Diagnostics/MonotonicNow/IsDisposed` 转发属性。退出顺序：池 → 流程。
- 接入层 `ResourceSystemSetup` 提供一次装配便利（创建缓存、加载器、工厂与共享默认项），**不新增 Builder、DI 容器或服务定位器**。

删除项：`ResourceManager._ownsFileCache`（赋值后无读取却在退出时无条件释放注入缓存）。

## 4. 主流程与四类事实

✅ **主线**：登记本轮请求与**唯一执行者** → 取得来源并发额度 → 执行后端 → 交付提交（判存活 → 登记产物 → 交付凭证 → 终结）或清理 → 终结记录。

个人退出只改变接收者集合：退出者只结束自己的等待；若接收者已空，则**在同一次提交内**关闭准入并标放弃，提交外只执行“已决定的后端取消通知”。**取消路径不再是第二个执行发起者**——被放弃且尚未取到额度的记录，由已在等待额度的原执行者走正常路径终结。

✅ **四类事实各自的结束条件**：

| 事实 | 表达什么 | 结束条件 |
| --- | --- | --- |
| 业务请求 | 某调用者自己的结果、取消与预算 | 交付、失败或个人退出 |
| 一次实际加载操作 | 真正的加载及本轮必要收尾 | 后端与收尾真实结束 |
| 具体产物 | 对象与唯一一份释放责任 | 责任执行完，或残留明确移交 |
| 引用凭证 | 某业务的一份持有 | 该凭证归还或失效 |

✅ **交付与清理**：后端返回后，在交付提交内、**任何用户回调之前**登记产物（`IsAssetAlive` 是引擎调用，必须在登记前完成）；无接收者时只撤下复用索引（`_DetachProduct`），产物保留在所有权集合里，仍可被业务卸载（R09/A07）。

✅ **一次释放**：未交付清理、业务卸载、退出释放共用「取得责任（`TryBeginUnload`）→ 执行 → 登记结果」；集合改动全部回到状态串行域。删除 `_CleanupAsync` 直调 `ReleaseAsync` 与域外 `_RemoveProduct` 的特殊路径。

✅ **`RetainAsync`**：取得持有属于提交类操作，统一经串行域提交，完成即已取得持有；不再保留“投递但同步返回”的混用契约。`IsValid` 只读本凭证（纯查询、任意线程）；产物是否可用由 `Value` 与诊断快照回答。

## 5. 实例池

✅ **保证级别**：只提供「有闲置就复用、无闲置就创建」，**无活跃硬上限、无池内排队、无 FIFO**。移除 `PoolPolicy.MaxActivePerResource` 及其整条调度职责；来源加载并发是另一项独立职责，保留不变。

✅ **原型持有**：桶为它所有在用实例**聚合持有一份**原型引用（不随租约数增长）；桶因真实依赖尚未结束而不能退出，是这项保证的成本。

✅ **清池规则（第 11–12 轮选定，GPT 第 12 轮确认）**：

1. **已接纳**＝已取到实例、或已发起本桶这次创建的租用；仍在等原型到位、尚未发起创建的不算。
2. 关闭后：已接纳的照常完成交付，租约归还时**直接销毁**；未接纳的以 `instance.pool_closed` 结束。
3. **桶已无原型使用者**＝无在用实例 && 无闲置实例 && 无已接纳的在途创建/销毁 && 无未确认结束的残留 && 原型获取已结束。

关闭动作：关新准入 → 取走并销毁**当前闲置实例** → 已在途创建真实结束后交付或清理 → 满足第 3 条时归还原型并摘表。

✅ **销毁失败**：`DestroyAsync` 抛错不必然证明对象还活着，能说明的是**没有依据断言它已安全结束**。因此对象与必要的原型依赖**继续由原桶的责任记录持有**，不计入在用、也不计入闲置，但阻止原型归还；**不新增第二份原型引用作保险**，也不以诊断裁剪撤销责任。责任结束只有一个条件：**对象已安全结束**，或已明确交接给另一份责任记录。📌 代价：桶因为真实依赖尚未结束而不能退出；没有安全结束依据时，责任不能按数量淘汰（本轮不引入残留容量系统）。

✅ **保留的必要保证**（有反例支撑）：`IsAlive` 查询异常不等于确认已销毁；实例 ID 防止旧租约误动同一实例；取消、创建失败、重置失败、清池交错下的确定终态与产物归属。**“每桶同时一次创建”已撤回**（第 13 轮），改为无闲置即直接创建；删除它不移除在途创建与迟到结果的所有权。

## 6. 文件层

✅ **共享粒度**：文件缓存按**文件身份**（`Source/Path/Revision/Variant`）共享一次填充；资源层按**资源身份**（`LocalKey`，含目标类型与转换参数）共享一次加载。两层各有必要，不重复记账——判据：一个 `LocalKey` 恰好对应一个缓存键，缓存层不知道资源层有几个接收者。

✅ **取消与收尾**：填充持有**自己的**操作令牌，不使用任何单个使用者的令牌；使用者的取消只结束自己的等待。最后一人退出 → 同一次提交内关闭该填充的准入并决定取消 → 提交外通知后端 → 原执行者观察真实结束、处理未发布文件（删临时文件、**不发布**）→ **收尾完成后才摘除登记**。期间新请求发现记录不接受加入，就独立等它结束再取得新机会，不继承前者的取消结果。

不发布的理由是**这轮已放弃、统一清理、不再转成缓存成功**；取消本身不证明内容更旧。收益是同键不会有两个生产者。

✅ **TTL 范围**：只约束**文件获取**，不约束内存产物。TTL 到期后：已有引用不变；同参数新 `Load` 命中内存产物、文件层不被调用；只有显式卸载后再次加载才真正进文件层。

✅ **时间基准（第 11–12 轮选定，GPT 第 12 轮确认）**：**全部写入结束后，由文件缓存显式写入 TTL 基准，再发布并开放读取**。顺序为“写临时文件 → 关闭写入句柄 → 缓存设置最后写入时间 → 改名到最终路径 → 开放读取”。`mtime` 是最后写入时间，不因把改名称作发布就变成发布时间（依据：[Microsoft 文件时间文档](https://learn.microsoft.com/en-us/windows/win32/sysinfo/file-times)）。不引入旁文件；边界是缓存目录由框架独占写入——允许外部修改时就不能同时承诺框架仍能识别原内容年龄。

✅ **删除策略**（R11/Q02）：与有效期分开；触发时机为初始化时一次；`StartupTargetBytes` 默认必须是有效值（`null`＝不清理不能作默认），具体目标由项目按“单文件大小量级 × 设备磁盘”给出（2 GiB 只是候选）。进程中断留下的 `.tmp` 由下次启动清理处理。

✅ **转换**：按目标类型精确注册的接口保留；本地与远程共用；转换注册表留在加载/转换装配处，不塞回文件缓存（换一种业务表示不应要求理解磁盘清理）。

## 7. 失败策略

✅ 个人取消、超时、类型不符、进度回调异常只影响本人。

✅ **所有来源统一接续（`ContinueWaitingRequests`），删除 `FailWaitingRequests` 及共同失败分支**。原文第 9 条要求“任何任务的失败/取消不会影响剩余任务的执行”，共同失败是压缩这项保证且无原文依据；唯一读取点只有 `ResourcePipeline.cs:1341-1346`，无已有消费需求。默认值修正由此升级为“只保留一条主流程”。

✅ **接续契约**：

1. 一次实际尝试只有一个承担者：本轮最早、且尚未承担过失败的仍在等待者。
2. 失败时只结算承担者；**接续只在原执行已结束之后开始**，不出现两次尝试并行。
3. 从尚未承担失败且仍在预算内的等待者中再选承担者，直至成功或没有可继续者。
4. 承担者中途取消：其承担者身份随退出结束，下一轮从剩余者重选；取消不消耗别人的机会。
5. “总尝试数 ≤ 最初请求数”只在没有新请求加入时成立；有新请求加入时以“每轮消耗一名承担者、不复用已承担者”为准，不写成固定上限。
6. **不新增核心隐式重试层**：每轮可以包含下载器配置的多次传输；接续形成的新调用仍会增加实际总传输次数，因此不写成“核心重试与传输重试不相乘”这种容易被读成“总次数不变”的说法。

✅ **承担者取消后的行为**（GPT 第 14 轮校准）：只要还有接收者，本轮共享后端**仍继续**；成功则交付剩余者，失败也**不把本次失败追记给别人**；原执行收尾后才选下一轮的承担者。

✅ **删除策略契约（装配保证有效）**：启用文件缓存时，接入装配必须提供有效的启动清理目标；**缺少目标则拒绝该缓存初始化**；初始化时按目标清理一次；核心不猜通用容量，也不承诺运行期磁盘硬配额。未使用文件缓存的装配不受此约束。`Forever` 只影响新鲜度，不绕过启动清理。

## 9. 文件清单（按真实执行职责计数）

**判据**：有实质执行逻辑（IO、并发、生命周期、映射）的文件按其执行职责计数，不借“Definition 目录”或类型名藏掉资源流程；纯数据契约、枚举、只做参数校验的配置类型才计入定义。**三种内置来源统一计入核心执行**（R01 要求内置，其实现即核心职责），**便利装配计入接入执行**（它只创建依赖并交出所有权，不含资源流程）。

**核心执行 10 份**（实施后：控制台程序集 9 份 + Unity 程序集 1 份）：

**结论**：核心执行 10 份，接入执行 1 份，定义 5 份，总计 16 份 + 2 份 Unity 程序集内实现 = 18 份；满足 R13“除定义代码外核心流程 ≤10”。

**实施与计划的偏差（必须写明）**：

1. `ExecutionContext` 保留在 `Definition/ResourceExecution.cs`，未改名为 `Core/ExecutionContext.cs`：它同时承载执行契约与内联实现，改名不改变职责，暂不动以减少无关 diff。
2. Unity 适配不放在 `Adapters/` 目录：`Tools.csproj` 通过 `<Compile Include="..\..\Unity\Assets\ToolKit\Tools\**\*.cs">` 把该目录编入**控制台程序集**，`UnityEngine` 依赖会直接让控制台构建失败。因此 Unity 实现放在 `Unity/Assets/UnityToolKit/Runtime/Resource/`，由 Unity 程序集编译；职责划分与 10/1/5 的计数不受影响。
3. Unity 侧代码在本环境**无法编译或运行**（无 Unity 程序集引用），属未验证范围，见第 12 节。

## 11. 实施顺序与重新删减要求

实施顺序（GPT 第 14 轮给定）：

1. **先固定已选契约与装配所有权**——配置快照、失败策略单一化、缓存目标由装配提供、谁创建谁关闭；先把保证定死，避免边改边变。
2. **收敛唯一执行与产物交接**——取消路径不再做第二个执行发起者；“登记前操作负责产物，登记后共用一份释放责任”；删除三处独立释放责任。
3. **移除池的额外调度**——活跃配额、FIFO、池内等待、单桶串行创建；同时保留在途创建、迟到结果、个人预算与闲置维护。
4. **落实文件流程与三种内置来源**——填充自有取消源与收尾后摘登记、TTL 基准写入、启动清理目标、Unity Resources 实现。

**实现完成后必须重新自查“能否再删去三分之一”**，不能以本方案的估算当作已实施结果，也不能用压缩排版达标。能删的是：不需要的职责、重复推进、重复责任；不能删的是：仍在使用的依赖、已启动工作的收尾。

**已落地**：

| 项 | 结果 |
| --- | --- |
| 装配所有权归位 | `ResourceManager` 不再创建／初始化／关闭 `FileCache`，删除 `_ownsFileCache`；装配与默认错误映射移入 `Adapters/ResourceSystemSetup.cs` |
| 初始化单一事实 | `IsInitialized` 由初始化任务状态决定：进行中与失败重试期间都为 false，成功才开放入口 |
| 失败策略统一 | 删除 `FailWaitingRequests` 与共同失败分支，所有来源接续；承担者失败仍标记 `MarkBorneFailure` |
| 唯一执行 | 新增 `TryClaimExecution` 原子认领；删除 `_AbandonAsync` 的第二个执行发起者（改为 `_StartExecution`） |
| 放弃决定合并 | “移除判空 + 关闭准入 + 标放弃”收进同一次提交，提交外只通知后端取消 |
| 统一产物责任 | `_CleanupAsync` 与业务卸载、退出共用 `TryBeginUnload → ReleaseAsync → 登记结果`；未登记产物由本轮操作释放 |
| 池调度删除 | 删除活跃配额、等待队列、`_Pump`/`PumpResult`/`RentRequest`、FIFO、每桶串行创建；改为无闲置即直接创建 |
| 清池准入 | 关闭桶不再服务新租用（换新桶），已接纳的照常交付、归还即销毁；删除 `Admitted` 冗余计数 |

| 文件填充 | 自己的令牌源 + 等待者计数；关准入后等真实结束才摘登记；取消不包装、不发布 |
| TTL | 发布后由缓存显式写 `LastWriteTimeUtc` 作为基准；有效期按本次请求给出，不再在构造时算一次 |

**测试**：控制台程序集 `69/69` 通过（ResourceSystem 61 项）。新增／改写用例覆盖：统一接续、每轮只消耗一名承担者、最后接收者取消不启动第二个执行循环、失效旧产物与新产物并存、没有闲置即各自创建、创建未完成即超时、闲置上限为零桶立即退出、**远端同文件不同表示共享一次下载**（此前零覆盖）、**先到者取消不终止另一表示**、**下载失败不发布缓存且可重试**、**归还投递不阻塞业务线程**（真实线程测量）、**帧驱动真非阻塞上下文下的并发取用／跨线程归还／失效后追加持有被拒**。

**Unity 适配层已通过编译验证**：用 `ToolKit/Tests/UnityAdapterCompileCheck`（引用本机 Unity 2021.3 的 `UnityEngine.CoreModule.dll`）把资源系统源码、其 Network 依赖与 Unity 侧适配一起编译——**0 错误、0 警告**，即 `UnityExecutionContext`／`UnityGameObjectFactory`／`ResourcesLoader` 确实实现了全部接口契约。该工程是临时校验用，不属于交付物、也不被 `ToolKit/Tests` 引用。
> 验证有效性经反向确认：把 `CanCreate` 改名后编译立即报 `CS0535 未实现接口成员`，说明这份检查真正在编译适配源码，不是空跑。

**编译验证发现并修复的真实缺陷**：`ToolKit.Tools.Common.ResourceRequest` 与 `UnityEngine.ResourceRequest` 同名——Unity 适配文件里未加限定的 `ResourceRequest` 会解析到引擎类型，导致接口未实现与歧义错误（`CS0535`/`CS0104`）。此前"只有静态审查"时不可能发现。修法是在两个适配文件加 `using ResourceRequest = ToolKit.Tools.Common.ResourceRequest;`。

**过程中发现并修正的自身缺陷**：

1. `Admitted` 计数在复用路径漏减，导致桶永不退出（已删除该冗余计数）。
2. `ClearPoolAsync` 就地把桶置 `Closed` 而 `RentAsync` 仍可能复用它（已改为换新桶）。
3. `_TryClose` 在持锁状态下摘表，已关闭桶留在索引里（已移出锁）。
4. 池预算到期被报成调用者取消（已按契约拆分为 `request.timeout`）。
5. **文件填充的取消所有权（设计缺陷）**：原实现"最后一个使用者退出即取消该次填充"。A05 用例暴露出：某个表示的解析/登记比先到者的取消晚一步时，后来的表示会**加入一个已被取消的填充**，从而继承别人的取消——正是需求禁止的行为，也是用例偶发失败的真因。已改为**使用者的取消只结束本人等待，不取消已经开始的一次填充**；填充令牌只在缓存退出时使用。填充结果对后来者同样可用，因此这也消去了同键重复下载。

**测试稳定性**：xunit 默认并行运行不同测试类，而默认执行上下文是进程级共享实例，互不相关的用例会争用同一个串行域；已用 `[Collection("ResourceSystem")]` 串行化。另有两个断言依赖时序（把尝试次数写死为 2；卸载前未等待持有归零），已改为断言契约本身。

**已知未解问题（如实记录）**：`ResourcePipelineTests.主动卸载只释放无人持有的产物并返回计数` 在**整套运行时**仍约 7%（修复前约 20%）偶发失败，单独运行 40 次不复现，其前置条件断言（两个地址的持有数）每次都成立。已在该用例内加诊断输出以便下次复现时定位；这是既有用例的时序敏感问题，不是本轮改动引入，也尚未定位到产品缺陷。

**未完成（不声称覆盖）**：真实 Unity PlayMode 运行（编译器引用的是本机 2021.3 程序集，项目自身为 6000.5.1f1，仅用于编译期校验）、真实网络／磁盘故障注入、AssetBundle 实机时序。`IExecutionContext` 的 Unity 实现需要项目在帧循环里调用 `Tick`，该驱动方式未在引擎内验证。

**计数偏差**：核心执行 9（控制台程序集）＋ 1（Unity 程序集 `ResourcesLoader`）＝10；接入执行 2（`ResourceSystemSetup` 便利装配 + `UnityAdapters`）；定义 5（`ResourceExecution` 含内联执行实现，按执行职责计入核心执行）。与需求的 10／2／6 口径一致。
