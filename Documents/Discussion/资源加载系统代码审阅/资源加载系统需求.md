## 设计阅读导引

先不讨论类名，用一个业务流程说明系统：A/B/C 请求同一资源 → 共享一次实际加载 → A 中途退出 → B/C 各自取得引用 → B 归还 → 业务发起清理 → C 仍能使用 → C 归还后对象可被清理。再把远程文件转换和实例租用接到这条主线上。

实现者需要首先回答：

| 设计问题 | 应说明的结果 |
| --- | --- |
| 谁决定做什么 | 业务决定来源、何时获取/归还/清理；框架保障约定的共享及所有权；后端完成具体加载。 |
| 哪些概念不能混为一谈 | 单个请求、一次实际操作、具体产物、业务引用有不同结束时刻；身份相同不代表是同一份对象。 |
| 谁拥有依赖 | 装配者明确创建、借用、共享或移交；使用一个组件不自动获得销毁它的权限。 |
| 哪些复杂度来自需求 | 独立取消、迟到结果及实例原型保护有直接依据；硬性活跃配额、FIFO、运行期刷新等须另给真实场景。 |
| 如何证明更简单 | 从入口能顺着读出主要阶段；每个阶段有推进者和产物所有者；能删掉重复决定及无需求的保证。 |

上述是职责，不预先要求拆成同样数量的类或接口。下文 R01–R13 给行为边界，Q01–Q04 记录设计选择及其确认状态，末尾场景用于检查推导结果。

## 1. 定位与边界

**R01（原始要求）**：面向多个 Unity 项目的通用加载框架，覆盖本地文件、远程文件、Unity Resources、AssetBundle 中的资产。业务指定来源，能自定义和替换加载器。内置前三种实现，不内置 AssetBundle 加载器。四种来源可以共用一个接口，不强制四套接口。

**R02（原文歧义，已认可的解释）**：原文同时写“提供 assetbundle 的管理”及“bundle 资源的管理由项目业务层自行维护”。双方认可：框架管理从 Bundle 取得的资产与引用；Bundle 容器、依赖、清单、版本、下载和生命周期归业务。资产的释放责任由后端交出，核心不擅自卸载整个 Bundle，也不在未交出释放责任时推断拥有底层对象。

不自动扩张的能力：资源内存硬配额、运行期磁盘硬配额、热更新系统、Bundle 依赖管理、独立停服排空、跨进程一致性。需要时另行明确，不能从“通用”推导。

## 2. 主流程与所有权

**R03（契约补充）**：配置与注册 → 初始化成功 → 解析身份 → 命中缓存或合并等待者 → 获得来源并发额度 → 实际加载及转换 → 为各接收者建立独立引用 → 批量完成通知 → 业务归还 → 业务选择卸载。

记录保存事实，编排者推进流程，后端完成具体操作。同一记录只有一个执行发起者，取消不另起执行循环。产物产生后，在必要验证及登记前由本轮实际操作负责；包括验证失败时的清理。尽早将有效产物交给唯一产物记录，登记后的未交付清理、业务卸载和退出共用该记录的释放责任。无人接收的迟到结果也有清理者。初始化成功才开放业务加载；保留初始化失败后重试，同轮及后续幂等调用必须观察一致结果。

**R04（原第 8 条及契约补充）**：获取结果返回资源引用或实例租约，不直接返回缺乏所有权说明的裸对象。有效包装允许读取对象；归还幂等，归还后该包装立即失效，即使同对象另有持有者也不恢复。追加持有产生独立引用。旧对象与同键新对象并存时，旧引用仍指向旧对象，旧清理不能移除新对象。

追加持有采用 `RetainAsync`，通过串行域完成条件检查及记账，完成即已取得独立引用。归还先使本人凭证失效，再投递记账；不能让别人的持有恢复本凭证的读取权。

## 3. 共享、失败与取消

**R05（原第 9 条）**：同资源并发请求只进入一次实际加载，其余异步等待；成功后批量交付并通知，不逐个重新加载。每个调用有独立结果和取消。

契约补充：个人取消、超时、类型不符或进度回调异常只影响本人；最后一个接收者退出后才可放弃共享后端。后端不能立即停止时，原操作负责迟到结果及清理。该规则必须覆盖不同转换表示共同依赖同一文件下载的组合路径。

来源及加载器解析出的稳定标识构成资源身份；影响结果的类型、版本、转换参数应进入相应身份。资源表示身份与下载文件身份可不同，但必须分别说明共享范围和取消所有权。

**Q01（已选定）**：所有来源统一接续等待请求，不保留 `FailWaitingRequests` 共同失败选项，不按 Local/Remote 隐含切换。每轮从尚未承担失败、仍在预算内的等待者中，选择最早者承担本次实际尝试。共享后端失败只结算承担者；其他请求在本次后端及收尾真实结束后保留后续尝试机会，无需业务重新调用。成功时批量交付全部合格接收者；没有可继续者时结束。

承担者提前取消只结束本人，仍有接收者时本轮后端继续：成功交付剩余者，失败也不把本次失败转嫁给其他请求；原操作收尾后再选下一轮承担者。固定一组请求中，每人至多承担一次失败；有新请求加入时，不能以最初请求数充当全局尝试上限。

一次后端调用可以包含下载实现配置的多次传输尝试；接续会形成新的后端调用，实际传输次数随各轮累积，并非天然不会相乘。核心不再叠加额外隐式重试层，各请求仍受自己的总预算与取消约束。

## 4. 配置与线程

**R06（原第 2 条）**：开放实际需要的并发、超时、重试、目录等配置，逐项说明对象范围、默认值、覆盖关系、生效时机和执行者。

- 来源并发统计实际不同资源操作，同键等待者不重复占额，不承诺严格 FIFO。
- 单请求超时覆盖从入口至交付的解析、额度等待、共享等待和接续；租用总预算覆盖原型获取及创建，不按阶段重新开始计时。实例池不再提供额度排队。
- 下载重试交给下载实现；核心不按来源名称再增加隐式重试。
- 目录、文件有效期、磁盘清理与池闲置缓存配置分开定义，不暴露无效字段。
- 装配时保存独立配置快照，不保存外部可直接改写的选项对象。

**R07（契约补充）**：明确状态串行域、Unity API 所需线程及各公共入口的线程约束。跨线程操作使用可等待调度，归还投递不阻塞业务线程。引用计数、索引、配额、卸载责任使用一致的同步规则。检查同步完成、真正异步、嵌套入口和回调重入，不能以 async/Task.Yield 单独证明安全。

## 5. 预加载、缓存与卸载

**R08（原第 3、4 条）**：支持预加载、产物缓存、实例池化。最小预加载可以是正常加载成功后归还引用，缓存保留，下一次相同请求不再加载。不因此强制新增批量调度器；批量入口、实例预热和进度聚合暂属可选提案。

**R09（原第 5 条及契约补充）**：业务决定何时、如何、清理多少及哪部分。归还只减少持有；卸载选定目标并在执行前复查持有。撤下复用索引但尚未释放的旧产物，仍应可被业务选择卸载。

一次失败不阻止其他项；结果区分成功、在用而跳过、失败及具体残留，不把尝试数量当成功数量。选择范围与数量采用最小必要接口，不预设预算系统。释放责任至多取得一次，失败不误伤同键新产物，不永久封锁资源键。

## 6. 实例池

**R10（原第 4、8 条及契约补充）**：原型获取 → 选择池桶 → 复用或创建 → 重置并交付租约 → 归还复用或销毁。活跃、创建中、闲置或销毁失败的实例仍依赖原型时，保持相应原型引用。

清理时明确哪些实例归池持有、哪些仍由业务持有；已有租约和实际使用的原型依赖不得因清理索引而失去保护。本轮采用关闭旧桶、桶聚合持有原型的模型，闲置实例、旧租约晚归还和在途创建均有清理者。聚合持有与是否提供配额排队是两个独立选择。取消、创建失败、重置失败及清理交错均有确定结果和产物归属。

**Q04（已选定）**：移除活跃硬上限、池内额度等待队列、FIFO 及单桶串行创建保证；无闲置时各租用直接创建，不按实例新增原型引用，原型由桶聚合持有。这不会移除在途创建、个人取消及迟到对象的所有权，也不会移除独立的每来源资源加载并发限制。保留闲置复用与必要清理；公开配置和行为变化须给迁移说明，不能静默忽略旧字段。

关闭旧桶时取走并销毁闲置实例，已有租约归还后直接销毁；所有实际对象及操作不再需要原型后才结束持有。**第 11–12 轮选定准入规则**：取得实例或开始本次创建算已接纳；仍在等待原型、尚未开始创建不算已接纳。关闭与越过准入点在同一串行规则下确定先后。已接纳且未取消的租用可以继续交付，随后归还即销毁；未接纳租用以池关闭结束，迟到原型归还。清池因此可能使已经调用、仍等原型的租用失败，这是明确选定的行为代价。

销毁未确认完成时，实际对象及必要原型仍由原桶负责；不增加第二份原型持有作为保险。诊断只描述责任，不因业务未读取报告、裁剪历史或调用清池/Dispose 就撤销依赖。没有安全结束依据时保留未完成残留；本轮不引入自动重试、残留容量系统或所有权移交 API。只有实际对象及操作均不再需要原型时，桶才结束相应持有。

GPT 在 v1 将 A11 写成无条件验收，是把当前实现能力当成必要需求的推断，现已撤回。第 8 轮实现方明确选择取消池配额及串行调度，当前 A11 因能力删减不纳入最终验收；不是用户更改原始要求，也不以删除行数作为裁决依据。

## 7. 远程落盘与转换

**R11（原第 6 条及远程段）**：远程内容先形成可复用本地文件，后续优先读取有效缓存；失败或取消的临时文件不成为有效缓存。落盘文件必须有实际生效的删除策略，不能无限累积。

选定流程：文件操作自有取消源；最后一个接收者退出时关闭准入并决定取消，原执行者观察真实结束、处理未发布文件，再摘除登记。期间新请求独立等待旧操作收尾，再争取新的获取机会，不继承旧请求的取消结果，也不启动第二个同键生产者。已放弃的填充统一清理，不把迟到成功转成缓存发布；这是收尾策略，不是判定内容新旧的依据。

TTL 只作用于实际文件获取；已有内存产物及同身份内存命中不因此自动刷新。业务卸载及引用规则仍独立生效。第 11–12 轮选定：填充全部写入结束并关闭写入句柄后，由文件缓存显式设置文件最后写入时间作为 TTL 基准，再改名发布并开放读取；不新增旁文件。缓存目录由框架独占写入，不承诺允许外部修改时仍识别原内容年龄。内容身份、新鲜度及删除策略不得混为同一保证。

**Q02（已选定）**：启用文件缓存时，接入装配必须提供有效的启动清理目标；缺少目标则拒绝该缓存初始化。初始化时按目标实际清理一次，核心不猜通用容量，也不承诺运行期磁盘硬配额。没有使用文件缓存的装配不受此约束。文件有效期与实际删除独立，Forever 也不绕过启动清理；标记过期不等于完成回收。启动清理继续处理上次中断留下的临时文件。

**R12（原第 7 条）**：开放转换接口，本地与远程文件共用。转换失败清理中间对象，清理再失败保留实际残留及原始原因。刷新不应交付半写入文件；是否需要运行期文件占用保护依据真实消费方式判断，不预先增加租约体系。

## 9. 最终修改方向与实施边界

### 职责及所有权

装配者创建和关闭文件缓存等共享依赖，核心管理器只接收使用权，不因使用依赖就获得销毁权限。管理器并列组织资源流程和实例池；池通过窄的原型获取能力使用资源流程，不让资源流程反过来管理池。正常退出先处理池，再处理资源流程；仍在使用或未确认结束的对象继续受既定责任记录保护，退出不等于可以强制释放。

请求记录描述个人结果与预算，操作记录推进唯一实际执行，产物记录负责具体对象，引用及租约表达业务持有。复用索引与全部责任记录用途不同：从复用索引撤下，不等于对象已释放或不能再被业务清理。外部回调和实际后端工作不塞进状态提交段；记录变更统一提交，随后通知业务。

### 模式、删减与保留依据

沿用已逐一对照 GoF 23 种模式后的四种组合：外观为主，由 ResourceManager 提供统一入口；策略承载可替换加载器、转换器和工厂；适配器衔接 Unity、下载及文件接口；观察者用于进度与结果通知。策略执行由流程编排，适配器实现具体边界，通知在状态确定后发出。无需新增全局事件中心、状态对象树、抽象工厂族或 DI 容器。

删除无需求依据的池活跃配额及串行调度、共同失败分支、取消路径的第二个执行发起者、各自认领释放的特殊路径；装配移出核心后删除无职责的转发及所有权字段。旁文件、自动刷新内存、残留第二份保险持有和残留容量系统均不引入。预计删减量是实施前估计，不能当作已删除行数。

### 公开接口迁移与验证

- Retain 改为可等待的 RetainAsync，调用方等待取得结果；这是签名及调用形态变化，仓内测试调用点不是全部外部消费者。
- 删除 MaxActivePerResource 及对应池调度，原依赖活跃上限的业务需自行承担限制；不依赖该保证的调用者删除配置即可。不保留忽略旧配置的兼容入口。

### 原文标题：通用资源加载系统需要
#### 定位
这是一个跨Unity项目的资源加载框架，能够加载管理本地文件/远程文件/Unity的Resource资源/Unity的Assetbundle资源。
#### 功能
1. 开放4中类型的加载器锲约，用户可自定义加载器。另外框架有内置加载器，但是Assetbundle加载器不会内置； 
2. 开放大量配置，包括并发、超时、重试、目录等等；
3. 支持资源预加载；
4. 支持资源缓存，实例资源池化；
5. 支持资源卸载/清理，由用户决定何时何地情况、如何清理、清理多少、清理哪部分；
6. 通过远程加载而下载到本地的文件资源，需要有删除策略，不能无限期保留；
7. 开放接口，可以将加载结果转换成业务所需的数据对象；
8. 不向外提供裸资源，通过合理的包装，让提供的资源可以方便的回收/清理，方便引用管理；
9. 合理的通知系统，对于多个业务加载同一个资源的情况，只有第一个任务会进入加载流程，其余任务会被阻塞，等待加载完成后一次性通知。任何任务的失败/取消不会影响剩余任务的执行；
##### 加载远程资源
成功加载的远程资源会优先存储到本地，下载同一个远程地址的加载，会转而优先从本地进行加载
##### Assetbundle资源加载
本框架提供assebundle的管理，只负责从其中加载的资源的管理。bundle资源的管理由项目业务层自行维护。
#### 现状分析与要求
当前的系统，脚本达到不可思议的30多个，代码可读性极差，流程不清晰。混乱无比。要求：除开定义代码。核心流程代码不超过10份。
