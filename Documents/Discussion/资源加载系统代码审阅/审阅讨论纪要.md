- 证据：`Core/ResourceRef.cs:43` 的 Value 只检查共享 `HoldCount`，未检查本引用 `_disposed`，也未执行注释承诺的存活查询。

- 对应 R04/A06。共享对象的持有数不能代替某张凭证自己的有效性。

#### G02｜P1｜初始化尚未成功已开放入口，重试后的幂等结果相互矛盾

- 证据：`Core/ResourceManager.cs:67,74` 在启动时置 `_initialized=1`，业务守卫仅检查该标志；`24,92` 的一次性 `_initialization` 失败后不重建。

- 对应 R03/A02。方向：明确初始化中的任务及成功状态；如果保留失败重试，所有调用观察当前轮结果；如果放弃重试，删除相反承诺。无须引入完整服务 Closing/Faulted 状态机。

#### G03｜P1｜旧产物撤下复用索引后，业务没有卸载入口

- 证据：`Core/ResourcePipeline.cs:730–733` 失效后仅 `_DetachProduct`；`759–765` 的业务卸载快照却只遍历 `_current`，而未释放对象留在 `_entries`。

- 方向：明确“可复用索引”和“仍由系统负责的产物集合”的职责；业务卸载选择后者，再按具体对象复查持有。不能为了只留一张表而让旧对象丢失所有者。

#### G04｜P1｜个人取消的两次提交之间，新等待者会被误伤

- 证据：`Core/ResourcePipeline.cs:297–309` 第一次提交移除旧请求并计算空集合；`320–333` 第二次提交不复查等待者数量，直接 MarkAbandoned 并取消后端。

#### G05｜P1｜未交付产物清理与退出清理可对同一对象释放两次

### 三、阻断问题：静态完整路径已确认，仍需针对性运行验收

#### G06｜P1｜文件层共享破坏资源层的独立取消

同 URL 转成 byte[] 和 string 时，`Loaders/RemoteFileLoader.cs:63–65` 形成不同资源表示，`77–81` 却复用同一文件填充。`Files/FileFill.cs:91,107` 使用首个调用的 token 驱动整个共享填充；后来的调用只等待共同 Task（`82–99`）。先到表示的最后调用者退出会取消共享下载，另一个表示随之失败。`146–154` 还把取消变成 FileIoFailed。

对应 R05/A05。请明确文件填充自己的操作生命周期及各使用者的等待生命周期；取消一个使用者不应取消仍有使用者的填充。此处不要求增加运行期文件租约或硬容量账本，解决的是正在执行的共享操作。完整验收必须经过两种转换入口，不能只测 ResourcePipeline 内部。

#### G07｜P1｜ClearPool 过早归还原型，旧实例晚归还后无人维护

`Core/InstancePool.cs:552–566` 将桶关闭并摘表，只销毁闲置实例便 ReleasePrototype；仍在用或创建中的实例没有保护。`352–390` 的归还没有检查 Closed，旧实例可能重新进入闲置，而旧桶已不受后续 Tick 管理。

反例：A 活跃 → ClearPool → UnloadUnused 可释放仍供 A 使用的原型 → A 归还后实例留在已摘表旧桶。创建中清池同样提前归还原型。

对应 R10/A10。方向：关闭停止新准入，旧桶继续承担已有租约和操作的清理；晚归还走销毁，最后实际使用及必要清理结束才归还原型。清池是局部生命周期，不能拿“不需要服务排空”作为删除它的理由。

#### G08｜P1｜实例池存在不能结束的请求，以及交付前对象丢失

- **创建中取消、迟到成功**：取消回调 `InstancePool.cs:903` 跳过 Started 请求；`301–318` 随后只销毁迟到实例，不完成该请求的 Waiter，`137` 继续等待。

- **OnRent 抛错丢对象**：`272` 已创建实例，`282` 重置抛错后 `291–296` 只结算创建失败，既无销毁也无残留登记。对象没有租约或清理者。
- **销毁失败不保留对象依赖**：`427–438` 报告错误后仍 EndDestroy，再尝试关闭；应说明失败对象及其原型依赖由谁继续持有，不能把诊断通知等同所有权移交。

对应 R10/A09–A11。方向：请求终态与对象清理分别完成；所有创建/复用结果在交付前有唯一暂管者；统一在容量或请求状态变化后推进桶，不继续添加散落的漏斗分支。

- **何时登记**：后端返回后，在**交付提交内、任何用户回调之前**登记。唯一执行者、串行域、尚无等待者被通知，这三点使“登记时刻”不含用户代码，重入不可能。
- **谁取得责任**：未交付清理、业务卸载、退出三条路径，谁先执行谁取得；取得失败（已在释放中）沿用同一份完成通知，不启动第二次释放。
- **失败后谁持有残留**：残留对象随 `DirtyResource` 进全局脏集合与本次卸载结果，`RetainedObjects` 落到具体对象；记录照常退出集合，**同键不被永久封锁**（`ResourcePipelineTests.cs:598-623` 已在守）。残留责任是“已明确移交”，不是“由框架继续持有”。

顺序上的一个必要调整：`IsAssetAlive` 是引擎调用，必须在登记前完成。所以交付提交是“判存活 → 登记 → 交付 → 无人接收则撤复用索引”。`_DetachProduct` 只撤复用索引、**保留在所有权集合里**，这正是 A07“旧产物仍可被业务卸载”的实现方式：失效只影响复用，不影响谁负责释放。

### 七、文件缓存：内置远程加载承诺什么

**先说清我撤回什么**：把默认改成 `Forever` 是我拿“少写状态”换了可观察行为——对动态 URL，`Forever` 等于“内容永不更新”，这是一次需求选择，不能由实现悄悄决定。撤回该提法。

事实从哪来：**发布时刻**。发布时把该内容的有效期写在与内容相邻的一份旁文件里（`{key}.bin.meta`），原子发布的一部分；读取时按“发布时间 + 期限 vs now”判断。这与“标记过期 ≠ 已删除”一致：过期只决定是否重新下载，删除仍由启动清理负责。不建索引表、不把有效期塞进 `FileIdentity`、不用展示格式参与身份。
