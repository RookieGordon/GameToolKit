## 1. 为什么要有这份策略

起因是一个问题：**"加载/下载任务失败或取消后，它的临时产物怎么办？"**

前一版设计只回答了"谁兜底"（框架在产物未交付时负责销毁），没有回答"策略是什么"。缺策略导致两个具体后果：

1. **把"策略"和"兜底"混成一件事**：兜底路径承担了本该由产生者解决的清理责任，成了常规路径。
2. **不同性质的东西被当成一类**：下载到一半的临时文件、已经发布可用的缓存文件、加载完成但无人接收的完整对象，被笼统叫"临时产物"，无法给出统一而又正确的处置。

---

## 2. 先分类：四类东西，处置方式本来就不同

| 类别 | 具体例子 | 是不是垃圾 |
| --- | --- | --- |
| **未完成的临时产物** | 下载到一半的 `*.tmp`、读到一半的字节数组、转换的中间对象 | 是 |
| **已发布的可用数据** | 落盘完成、校验通过的缓存文件 | **不是**——是缓存，有复用价值 |
| **无人接收的完整产物** | 加载已完成、但接收者已全部退出的对象 | 对本次而言是，但它**内容完整**，不能当损坏品处理 |
| **失败的证据** | 失败原因、实际残留对象 | 不是——是诊断与残留责任 |

**把这四类混成"临时产物"就没法定策略**，这是之前含糊的根源。

---

## 3. 已确认的策略 ✅

### 3.1 总原则 ✅

> **谁产生，谁销毁；产生者无法销毁时，显式交出残留。**

"显式交出残留"用框架里已有的机制表达，不新增概念：
- `ResourceLoadException.CleanupRemainders`——交出**具体对象**（需求第 7 条原文即要求）；
- `LoadError.Cleanup`（`Complete` / `Incomplete` / `Unknown`）——说明**这次回退是否完成**。

### 3.2 逐类处置 ✅

| 类别 | 结局 | 处置 |
| --- | --- | --- |
| **远端下载产生的临时文件** | 取消 / 失败 | **不删除**，留作断点续传 |
| **远端下载的已发布文件** | 发布成功 | 保留为缓存条目，受启动清理目标容量管理 |
| **其他数据**（本地中转产物、转换中间对象、读了一半的内存数据） | 任何非成功结局 | **直接删除**，不保留 |
| **无人接收的完整产物** | 接收者全部退出 | 销毁（走正常释放路径，不诊断为损坏） |
| **清理失败留下的东西** | — | **移入隔离通道**，与完整数据分开存放，打日志 |

**关键顺序**：失败/取消时**先销毁、再向上报结局**。顺序不能反，否则"报告失败"与"留下垃圾"之间存在窗口。

### 3.3 三条边界 ✅

1. **已发布的数据与本次结局解耦**。一旦发布成功，它就是缓存条目，不因为启动这次加载的请求后来取消而删除。理由：内容完整、校验通过、后续请求能直接命中；删掉只会让下一次重新下载。**"操作取消了但缓存文件还在"不是漏洞，是有意的。**
2. **无人接收的完整产物不当损坏品**。它内容有效，只是没人要；销毁走正常释放路径，不带"内容损坏"类诊断码。
3. **放弃续传能力是有意选择**。取消即删临时文件意味着重试要重新下载——除了远端下载这一类（见 3.2）。

---

## 4. 续传：光"不删临时文件"续不上 🔶

你定了"远端下载的临时文件一般不删，留作断点续传"。作为策略成立，但要真能续上，还差三件事——**这三条不解决，留下的就只是一个下次读不到的文件**：

| 缺口 | 现状 | 为什么不行 |
| --- | --- | --- |
| **部分文件要可寻址** 🔶 | 临时名是 `最终路径 + Guid + ".tmp"`，每次都是新 Guid | 下次找不到它，只能等启动清理删掉 |
| **必须记录已下载偏移** 🔶 | 无 | HTTP `Range` 要求偏移精确；不能靠"文件多大就是下了多少"（写入缓冲未必落盘） |
| **必须校验远端未变** 🔶 | 无 | 内容变了还接着写，会把两个版本拼成一个文件 → **静默数据损坏**，比重新下载严重 |

**我的提议**：

- 三条都归**下载实现**（`ToolKit.Tools.Network`）负责。`Range`、`ETag`、`Last-Modified`、重试本来就是传输层的事，文件缓存不该理解 HTTP。
- **文件缓存只保证一件事**：不擅自删除由它分配、但尚未发布成功的临时文件；删不删的决定权交给产生者。
- 部分文件按**内容身份**（现成的 `FileIdentity`）确定性命名，便于下载实现下次寻址。

**另外需要一条保留上限** ⏳：续传文件不设上限会无限累积，与"落盘文件必须有实际生效的删除策略"（R11）冲突。需要一个上限或有效期——是并入启动清理的目标容量，还是单独配一项，请你定。

## 5. 隔离通道 🔶

"清理失败的东西，走隔离通道，打个日志就行"。

我的提议：

| 项 | 提议 |
| --- | --- |
| 位置 | 缓存根目录下的 `quarantine/`——与正常缓存条目分开，保证一条扫描规则不会误删正常缓存 |
| 动作 | 把失败残留**移动**过去（同卷上是改名，成本极低）；移动失败则退回"留在原地 + 报未完成" |
| 记录 | 日志带**身份、原路径、失败原因、隔离路径**——原路径必须记，否则无法人工处置 |
| 自动回收 | **不参与**启动清理的容量计算。否则"隔离"等于延迟删除，人工排查窗口就没了 |
| 状态表达 | 移入隔离成功 → `CleanupStatus.Complete`（责任已明确交接）；连隔离都失败 → `CleanupStatus.Incomplete`，并**必须**通过 `CleanupRemainders` 交出对象 |

即：**"隔离"是残留的一个去处，不是第四种状态。** 不新增枚举值。🔶

## 6. 顺带发现的一处实现缺口 ✅（问题确认）

你提这个问题的直接动因是"取消了为什么还留着中间产物"。我核了代码，**确实有一处**，在内置文件转换器里：

`BytesFileConverter` / `TextFileConverter`（`Files/FileCache.cs`）当前是：

```
cancellationToken.ThrowIfCancellationRequested();   // 只在入口检查一次
var bytes = ResourceFileIo.ReadAllBytes(path, ...); // 不可中断的整文件读
return Task.FromResult(LoadedAsset.FromUnmanaged(bytes));  // 读完就交出
```

于是存在这个时序：**令牌在整文件读期间被取消 → 读照旧跑到完 → 一个没人要的产物被交出来**。
大文件（几十 MB 的配置表、从 bundle 提取物）这个窗口是**几百毫秒级**，不是几微秒。

**要改成**（✅ 已同意修）：分块读 + 每块检查令牌；返回前再检查一次，已取消则不交出产物。

同时补一条契约（🔶 提议）：`IResourceLoader.LoadAsync` 与 `IFileResourceConverter.ConvertAsync` 都写明——**交出产物之前必须检查操作令牌，已取消就不要交出**，而不是交出后让框架收尾。内置的 `LocalFileLoader` / `RemoteFileLoader` 照此补检查。

## 7. 框架那条"未交付产物"路径的定位 🔶

修完第 6 节的缺口后，剩下的窗口只有"后端返回产物"到"提交登记"之间那几条指令。框架仍保留这条兜底路径（不删已承诺的保证），但它应从**常规路径降级为兜底**，只覆盖：

- 上述极小窗口；
- 自定义加载器/转换器违反"已取消不交出"契约的情况。

**这条路径的存在理由**：`LoadedAsset` 只有框架知道该释放，产物在交付前没有任何业务持有者，所以必须有人对它负责。

## 8. 待你定的事项汇总

| 序号 | 事项 | 我的倾向 |
| --- | --- | --- |
| 1 | 续传三件事（确定性命名、准确偏移、`ETag` 校验）是否都归下载实现 | 是，文件缓存不实现传输逻辑 |
| 2 | 续传文件的保留上限怎么定 | 单独配一项，不并入启动清理容量 |
| 3 | 填充怎么声明"部分数据要留"（见下） | 甲 |
| 4 | 隔离区位置与"不参与启动清理容量"是否采纳 | 采纳 |
| 5 | 交出产物前检查令牌，是否写进契约 | 写进契约 |

**第 3 项的两种写法**：现在 `FileFill` 是 `delegate Task FileFill(string temporaryPath, CancellationToken)`，取消时缓存**无条件删**临时文件。

- **甲**：填充自己把部分数据搬到自己管理的续传目录——缓存零改动、不改公开签名；代价是每个远端填充都要记得搬。
- **乙**：`FileFill` 返回一个处置枚举（删 / 留）——语义集中在缓存里；代价是改公开委托签名。
