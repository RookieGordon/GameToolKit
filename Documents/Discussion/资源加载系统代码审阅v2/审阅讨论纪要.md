### 一、先说明是谁结束了谁，再决定锁的取消接口

按来源区别共享失败已经是需求；材料给出的映射是 AB / Resources / Local 整批失败、Remote 保留其他请求接续机会。**共享后端失败、某个调用者自己取消、业务主动终止一批等待者，是三个不同事件。** 来源失败策略不自动决定后两者，也不要求资源系统立刻改用 KeyedAsyncLock。

建议锁继续只提供“影响当前等待队列”的明确能力，由资源编排者决定何时调用；仅本人结束时不调用批次接口即可。这样无需为完整二维表增加一个无操作的 None 参数。保留已有 FailWaitingRequests 的单参数签名，是否新增 CancelWaitingRequests，先由下面的原因语义确定。仓内没有生产消费者只能说明已知调用范围，不能证明改公开签名没有外部兼容成本。

你提议批次取消时给每人填自己的令牌，理由却是方便业务判断“是否本人取消”。看一个直接例子：A 触发整批结束，B 的令牌没有取消；若 B 收到携带自己令牌的取消异常，B 的令牌仍未被请求取消，不能把这个结果解释成“B 自己退出”。**个人取消使用个人原因，批次终止使用真实批次原因，不借用一个没有发生的原因。** 如果决定以取消任务表达组终止，就明确它代表谁的决定，不伪装成个人取消；方法所收令牌也应有清楚用途。

“当前批次”还要确定一次边界。[现有锁](D:/Workspace/Porjects/GameToolKit/Unity/Assets/ToolKit/Tools/Common/AsyncLockSystem/KeyedAsyncLock.cs:103)每次调用都处理当时队列：H 先结束 B，C 随后加入，H 再调用一次，C 也会结束。TrySet… 只能说明同一节点不会重复完成，不能推出“方法重复调用永不影响后来请求”。我建议先沿用“每次调用独立作用于当时队列”，删去笼统的跨调用幂等承诺；若确需同一次业务失败被多处重复上报仍不影响 C，再说明固定批次身份的必要性。通知仍不释放执行权，持有者完成清理后才 Dispose。

**请用自己的话走一遍 H/B/C 的过程：H 本人取消、H 的共享操作失败、H 主动取消当前队列，各使谁得到什么结果？H 通知两次之间新来的 C 是否应受影响？** 先把这张结果表说清，再定方法签名。

### 二、续传数据从一开始归谁，而不是失败后谁抢救它

当前资源直调下载仍是从头写入，旧下载队列里的 Range 路径不等于资源加载已经支持续传；FileCache 目前的实际行为也已变成使用者退出后继续填充。因此“远端部分文件保留续传”是本次要补的端到端能力，不能只把缓存里的删除语句去掉。

我倾向把你的甲方案改得更直接：**下载实现从一开始就持有可再次定位的部分数据，失败/取消时留在其管理范围；完成、关闭句柄并验证后，再把完整内容交给 FileCache 的本次发布路径。** 缓存负责完整文件发布，下载实现负责续传位置、远端验证和何时重来。接入层传稳定身份即可，不必让 Network 依赖 ResourceSystem 的具体 FileIdentity 类型。

相比“先写缓存临时文件，失败后再搬去续传目录”，这一方案少一次失败时反向交接。代价是下载实现要明确工作区及保留责任。你的乙方案返回“删/留”枚举不能独自处理抛异常的路径：抛出之后没有正常返回值；若选择乙，就要解释处置决定通过什么通道到达缓存，而不是只改返回类型。

准确偏移是正确性要求，**不自动等于必须再保存一份偏移数字**。顺序写入真正停止并关句柄后，文件长度是否就是可靠前缀，取决于写入模型；先说明长度不够表达哪个事实，再决定额外记录。远端是否仍为同一表示需要独立验证，不能靠 URL 不变推断；例如 HTTP If-Range 使用验证条件决定继续区间还是接收完整表示，这类判断属于下载实现。[依据：RFC 9110 §13.1.5](https://www.rfc-editor.org/rfc/rfc9110.html#name-if-range)。

续传文件是有意保留的可复用数据，不是清理失败的隔离残留。它应有实际淘汰规则；先比较并入现有总磁盘目标、按类别安排清理顺序，与单独设置保留期限/容量的代价，不预先为每一类都增加一组配置。正在写入的数据由产生者保护，启动扫描不能机械删除全部 .tmp。

**请串起两次请求：首次中断 → 部分内容由谁持有 → 下次如何找到它并判断续传或重来 → 完整数据何时交给缓存 → 从此谁有权删除。** 说明当前“个人退出后继续填充”是否保留；个人取消和真实下载停止不能混成同一时刻。

### 三、隔离可以接管责任，但换目录和写日志不是接管本身

隔离需求已确定，具体模型仍需按对象性质说明。文件可以移动到隔离目录；Unity 对象、原型依赖和托管中间对象不能套用同一种“移动文件”动作。它们可以共享“退出正常复用、进入明确残留处理范围”的原则，而不必强行共用存储方式。

现有 CleanupStatus 描述本次尚未交付所有权的回退情况，报告也已声明不转移所有权。若隔离入口确实接管了文件及必要信息，本次操作的处置责任可以结束；但文件仍存在、仍须可查和有后续负责者。**若只是改路径加日志，却没有谁接管后续留存与回收，就不能凭移动成功宣布责任完成。** 内存对象隔离仍须由记录保护其实际依赖，不把日志当成所有者。

隔离区排除正常缓存扫描可以避免误复用和误清理，但“不参加这一种扫描”不等于“永久排除所有维护”。共用总容量并给隔离留存优先级，或使用独立保留窗口，都可以讨论；选择取决于排查窗口需求，不先造一套隔离框架。请同时说明日志无人查看时，由哪个现有职责继续负责。

还有一个与两篇材料都有关的顺序：**个人请求可以及时结束，操作收尾及责任交接必须真实完成后才能宣告相应操作完成。** 不要把“先处置再上报操作结局”推导成每个个人取消都必须等不可中断的 I/O 清理。后端交出前负责自己持有的产物，框架接到后负责交付或释放；返回前检查令牌可以减少无效工作，却不能消除等待状态提交期间的取消。框架处理无人接收产物是正常交接流程的一部分，不能仅以“窗口很小”或“只防违规后端”解释它。

**请给出一条隔离时序：销毁失败 → 谁实际接管对象及依赖 → 本次返回什么清理状态 → 后续由谁在什么条件下回收。** 再用“业务不看日志”和“个人请求先取消”检查这个回答是否仍成立。

### 一、H / B / C 结果表：三个事件各使谁得到什么

先定三个事件，再定范围：

| 事件 | 谁发起 | 影响范围 | 结果类型 |
| --- | --- | --- | --- |
| E1 共享操作失败 | 后端 | 按来源策略：本地类整批、远端仅起算的那批尝试 | 真实失败原因 |
| E2 调用者结束自己的等待 | 某个调用者 | **仅本人** | 个人取消 / 个人超时 |
| E3 业务终止一批等待者 | 业务（如管理器退出、来源替换） | 当时队列 | **真实批次原因** |

走一遍 H/B/C（H 是执行者，B 先加入，C 后加入）：

| 事件 | H | B | C（H 通知两次之间加入） |
| --- | --- | --- | --- |
| **H 本人取消**（E2） | 个人取消结束；共享操作**不因此停**（B/C 仍要） | 不受影响 | 不受影响 |
| **H 的共享操作失败**（E1，本地类来源） | 收到真实失败 | **收到同一个真实失败**，不重新调用即可确定结果 | 同 B |
| **H 的共享操作失败**（E1，远端来源） | 收到真实失败 | 保留自己的尝试机会 | 同 B |
| **H 主动终止当前队列**（E3） | 不受影响（它在队列外） | 收到**批次终止原因** | **不受影响**——C 在调用之后才到，不属于"当时队列" |

**"H 通知两次之间新来的 C 是否应受影响"：不应。** 每次调用独立作用于调用时的队列；第二次调用结束的是"那时队列里的人"。所以我不再承诺"跨调用幂等"这类笼统说法——`TrySet…` 只能保证同一节点不重复完成。

**上表还带出一个我之前没正视的问题**：本地类来源选"整批失败"之后，等待者如果按现在的逻辑"重新解析、再试一次"，对确定性失败就是**重复做注定失败的工作**（文件仍然不存在）。所以接续动作应当按失败性质区分：

- **确定性失败**（本地文件缺失、内容校验不过）→ 等待者**直接结算为同一个失败**，不重试；
- **瞬时失败**（远端网络）→ 保留尝试机会。

我的倾向是**不新增枚举**，让加载器对自己交出的失败负责声明是否确定性——但这会改加载器失败的契约面，我需要你判断：是加一个失败性质标记，还是由编排者按来源推断（用已有的来源策略顺带决定"要不要重试"）。**我倾向前者，因为来源相同也可能出现瞬时失败（远端文件系统错误），按来源推断会误判。**

### 二、两次请求串起来

**首次中断：部分内容归谁**

按你的建议改成更直接的一条：**下载实现从一开始就持有可再次定位的部分数据**，放在它自己的工作区，失败/取消时留在那里。`FileCache` 只负责**完整文件的发布**，不再承担"先写临时文件、失败后再搬走"的反向交接。

**下次怎么找到它、怎么判断续传还是重来**

- 找到：接入层给**稳定身份**（内容身份，与 `FileCache` 的 `FileIdentity` 解耦），下载实现按它定位自己的工作区文件；
- 判断：由下载实现做条件验证（`If-Range` 一类），**远端表示未变才续写，变了就整份重来**；
- **长度够不够表达"可靠前缀"**：顺序写入真正停止并关闭句柄之后，长度通常就是可靠前缀；不够表达的是"写入曾被缓冲、未必落盘"这件事。我倾向**先只依赖长度**，并明确要求"停止写入 → 关句柄 → 再读长度"；如果实现做不到这个顺序，才需要额外记录。这样不预先加一个偏移数字。

**完整数据何时交给缓存、从此谁有权删**

- 交接点：下载实现完成写入、关闭句柄、通过验证之后，把**完整文件**交给 `FileCache` 的发布路径；
- 交接后：缓存持有并有权删除（受总磁盘目标管理）；**下载实现同时在交接成功后丢掉自己的工作区**，避免同一份内容留两处；
- 交接前中断：文件在下载实现的工作区，缓存**看不到也不管**。

**个人退出后是否继续填充**

**分割线画在资源层，不画在文件层。** 理由：文件层无法判断"这个文件以后还会不会有人要"（不同表示会陆续到达，A05 用例正是这个形态），而资源层有接收者名册，能判断。所以——

- 文件层：**不因使用者退出而取消填充**（保持现在的行为，这修掉的是"后到的表示加入一个已被取消的填充"那个缺陷）；
- 资源层：**最后一个接收者退出时停止共享操作**，这个计数记在资源层。

**个人取消与"真实下载停止"是两个时刻**：个人取消立即结束该调用者的等待；下载停止只在最后一个接收者退出时发生，且停止请求不保证立即生效（后端可能已经跑完）。

**顺带解决你说的 `.tmp` 扫描冲突**：既然工作区归下载实现，**它就不该放在缓存目录里**（建议放项目持久化目录下的独立工作区）。缓存目录于是只含正常缓存条目，启动扫描**可以继续只扫自己的目录**，不会误删正在写入的数据；下载工作区由下载实现自己回收。

### 三、隔离时序

**销毁失败 → 谁实际接管 → 本次返回什么清理状态 → 后续谁在什么条件下回收**

先按对象性质分两路（`CleanupStatus` 描述的是**本次操作尚未交付的所有权**，不是"东西已不存在"）：

| 类别 | 谁接管 | 本次 `CleanupStatus` | 后续回收者 |
| --- | --- | --- | --- |
| **内存对象及其依赖**（Unity 对象、原型依赖、托管中间对象） | **原产物记录 / 原池桶继续保护**，责任不离开记录 | `Complete`——责任落在明确的所有者上，本次操作不再持有 | 该记录/桶：依赖真实结束后释放；退出时按既有路径处理 |

# 候选最终稿：产物处理、取消传播与回收范围

## 一、来源失败传播：落在资源编排的哪个决定点

**落点**：资源编排在**一次共享尝试收尾、结算本轮接收者**的那一步——即今天 `ResourceRecord.Complete` 决定"承担者失败、其余接续"的地方。加载器不变：**只交真实失败原因，不做失败性质分类**。

| 来源 | 本轮共享尝试失败后 | 其余等待者 |
| --- | --- | --- |
| AB / Resources / Local | 结算当前共享批次 | 收到**同一个真实原因**，不需要重新调用 |
| Remote | 仅结算本轮承担者 | 保留自己的尝试机会（重新解析、复查、继续） |

依据是用户已确认的按来源区分。**不叠加"确定性/瞬时"分类**：来源策略直接决定传播行为，不需要预测"是否永远失败"，也不新增错误性质标记。

## 二、三层取消：谁结束谁

| 层次 | 结束的含义 | 谁能让它停 | 遇取消时收到什么 |
| --- | --- | --- | --- |
| **个人请求** | 取消立即结束本人等待 | 调用者自己的令牌 | `OperationCanceledException`，携带**个人令牌** |
| **某份资源操作** | 无接收者时结束自己的等待或转换；不取消其他表示共享的文件填充 | 该记录（`CancelBackend`，只作用于自己的操作令牌） | 按该记录的策略结算 |
| **文件操作** | 使用者全部退出仍继续，直至成功、真实失败，或**所属生命周期要求取消** | 文件操作自己的所有者（`FileCache` 退出） | 该次填充自己的令牌 |

**不因第一个调用者取消而开锁**；**资源记录无权发"停止填充"通知**。

## 三、锁的公开契约（`KeyedAsyncLock`）

```csharp
// 保留原签名不变

// 新增：真实批次原因由发起组取消的所有者提供
public void CancelWaitingRequests(CancellationToken batchCancellation);
```

| 规则 | 内容 |
| --- | --- |
| 参数校验 | 令牌**未处于已请求取消状态**或为 `None` → 抛 `ArgumentException`，**不清空队列** |
| 受影响者收到 | **该真实批次令牌**（不是各人自己的令牌） |
| 作用范围 | **每次调用只作用于调用时已在队列中的节点**；之后加入的不受影响 |
| 节点完成次数 | 至多一次；个人取消与组取消相遇时，**以串行处理时首先完成的结果为准**，已交出结果不改写原因 |
| 已取消的个人请求 | 不入队（`LockAsync` 现有行为） |
| 执行权 | 两种通知都**不释放**持有者；持有者完成清理后才 `Dispose` |

**用 B 验证**：B 的个人令牌从未被取消，却收到批次取消结果；它从异常的 `CancellationToken` 看到的是**批次令牌**，因此能分辨"这是组取消，不是我退出"。

## 四、责任与回收范围

### 4.1 文件类：每一处都有直接负责者

| 路径 | 谁负责 | 失败/结束时 |
| --- | --- | --- |
| **缓存暂存路径** | **`FileCache` 从分配起负责**；下载方只借用它写入 | 下载方**停止写入、关闭句柄**后结束 `fill`；之后由缓存清理或隔离。**缓存必须等 `fill` 实际结束、写入停止之后才处理该路径**；个人请求先取消 ≠ `fill` 已结束 |
| **发布后的正常缓存条目** | `FileCache` | 启动维护：根目录全部非暂存文件（含不同 revision、不同变体）纳入同一目标容量，按最旧优先淘汰 |
| **下载工作区（续传数据）** | **下载实现** | 初始化先维护、后开放新下载；超出保留目标时按最旧写入时间淘汰 |
| **隔离区** | `FileCache`（缓存根目录下，同一目标容量） | 回收顺序：**正常缓存先、隔离最后** |
| 日志 | 谁都不接管 | 仅观察 |

**`fill` 成功返回是"完整产物的接收点"**，但**不是暂存路径清理责任的起点**——暂存路径从分配起就归缓存。

**发布失败**（缓存已接收但发布失败）：**缓存收尾**（删除或隔离），下载方不再持有。

### 4.2 一条完整过程：v1 发布 → v2 发布 → 业务仍按 v1 请求

1. v1 以身份（含 revision）为键发布文件；2. v2 发布另一个文件；
3. 两个业务**可以同时**持有不同 revision，也可能**回退**到先前版本——所以"看到 v2"**推不出**"v1 已无效或无人使用"，框架不建"当前版本"清单；
4. 两份都是正常缓存条目；下次启动维护**一并**纳入容量统计，按最旧优先决定是否淘汰；未超目标则可能继续保留（**不能写成"下次启动必删"**）。

**身份、有效性、回收各管一段**：身份由键表达；有效性由请求给的有效期与远端验证表达；回收由启动维护按容量表达。

### 4.3 一条完整过程：带可续传部分文件重启

上次进程中断，留下部分文件与续传所需信息 → 重启时**容量未超目标** → 该文件**不删除**，仍为续传候选 → 下次请求按稳定身份找回，**由下载实现验证远端表示是否未变**，决定继续写入或整份重来 → 未超目标时可能长期保留；超出时按最旧写入时间淘汰（**容量淘汰意味着放弃这次复用机会**）。

**启动维护不得把工作区内的可续传候选一并清掉。** 启动阶段没有写入者，需要解决的只是"删除时机"；**保留哪些文件由续传与容量策略决定，不由"上一进程遗留"决定**——遗留只说明产生时间，超目标只说明需要淘汰，两者都不能证明文件无效。

### 4.4 一条完整过程：`fill` 写了一部分缓存暂存后失败

1. 缓存分配暂存路径 → 下载方向该路径写入；
2. 下载方停止写入并关闭句柄，`fill` 以失败结束（保留自己的工作区续传数据，不动缓存暂存）；
3. **缓存**处理这条失败路径：清理或移入隔离；
4. 清理失败 → `Incomplete`，残留报告写明**已隔离到哪里、仍由谁负责**。

## 五、清理状态：保留原义

| 情形 | 返回 |
| --- | --- |
| 确已清理完成 | `Complete` |

### 1. 需求与失败传播

本轮依据用户直接确认的三项需求：**远端部分文件保留续传、清理失败隔离、按来源区分失败传播**。这是对上一轮部分选择的需求调整，不将旧选择倒写为误删。

| 来源 | 一次共享尝试真实失败后的结果 |
| --- | --- |
| AssetBundle / Resources / Local | 当前共享批次中仍有效的接收者共同结束，收到同一个真实失败原因 |
| Remote | 本轮承担者失败，其余仍符合原预算与尝试条件的请求保留接续机会，无需业务重新调用 |

这张表是**固定规则**，在资源编排的共享尝试结算点（当前 ResourceRecord.Complete 对应位置）表达一次，使用现有 ResourceSource。替换 Local 等来源的加载器不改变该来源的传播行为。不恢复 LoaderPolicy 的可覆盖失败配置，不增加第二份映射或“确定性/瞬时”分类。加载器只交真实原因；个人取消、超时和生命周期结束继续使用各自的结束规则，不套用共享加载失败表。

当前批次由该次资源结算取走的接收者名册确定；已结束的个人请求不被改写结果，之后的请求进入后续流程。资源系统继续使用现有合并与交付流程，本轮不改用 KeyedAsyncLock。

### 2. 主流程、三层结束时刻与产物责任

主线为：装配提供有效维护目标 → 初始化先维护、再开放使用 → 资源命中或合并 → 文件命中或共享填充 → 下载实现取得完整且验证通过的内容 → 写入缓存分配的暂存路径并结束写入 → fill 成功返回 → FileCache 发布 → 转换与资源交付 → 各层按自身所有权收尾。

| 范围 | 谁负责、何时结束 |
| --- | --- |
| 个人请求 | 调用者取消只结束本人等待，携带本人令牌；不等于共享操作已停止 |
| 一份资源操作 | 记录取消自己的等待或转换；不能取消其他表示共享的文件填充。无人接收的迟到产物仍须由实际操作及产物记录按正常交接流程释放 |
| 文件操作 | 使用者全部退出仍继续，直到成功、真实失败或 FileCache 所属生命周期取消；成功即发布为正常缓存。原执行者确认实际结束并完成收尾后，才结束该操作的登记 |
| 下载工作区 | 下载实现持有部分数据及续传所需信息，维护自己的工作区；不让 Network 依赖 ResourceSystem 的具体 FileIdentity 类型 |
| 缓存暂存及发布文件 | FileCache 从分配暂存路径起负责。下载方只借写，fill 实际结束前须停止写入并关闭句柄；之后由缓存发布、清理或隔离 |

**fill 成功返回是完整产物可接收、可发布的信号，不是暂存路径清理责任的起点。** fill 失败时下载方保留自己的续传数据，缓存处理自己的暂存；发布失败也由缓存收尾。双方不重复清理缓存暂存路径。个人请求先取消不能使缓存提前删除仍在写入的文件。

### 3. 续传、回收与隔离

下载从一开始就在下载实现管理的稳定工作区保留可再次定位的部分数据。顺序写入停止并关闭句柄后，以实际可靠前缀确定偏移，不另建重复偏移账。下次按稳定身份找到候选，由下载实现验证远端仍是同一表示、前缀可继续使用，才续写；无法成立时整份重来，不能仅凭 URL 相同继续拼接。

进程重启不会自动使部分文件无效：启动时先处理已确认不可用的数据，其余候选纳入工作区保留目标，超目标按最后写入时间最旧优先淘汰。未超目标时可继续保留；淘汰意味着放弃该份数据的复用机会。排序时间不承担内容一致性验证。

| 下载工作区 | 下载实现初始化先维护、后开放下载，使用装配显式提供的有效保留目标 |
| 缓存文件隔离区 | 位于缓存根目录下，由 FileCache 负责，与正常缓存共用容量目标；正常缓存先回收、隔离最后回收 |
| 清理失败的内存对象及依赖 | 原产物记录或原池桶继续保管；不增加第二份原型持有作为保险，不以诊断记录代替实际责任 |

维护只提供选定的启动清理行为，**不保证运行期占用上界，也不保证隔离最短保留时间**。长会话可能超过启动目标。工作区按容量淘汰、正常缓存及隔离按既定优先级回收，均不意味着每个文件下次启动必删。维护发生在开放使用之前；本轮不引入运行期扫描、当前版本索引或跨组件总配额协调器。

## 实施记录补充｜加载器与转换器的职责分离｜2026-10-16

用户指出：**加载器就负责加载，转换器就负责转换，两者的输入输出必须不同**。核对后确认这批评成立，而且我找到了真实证据：`Backup/Resource/Conversion/UnityImageFileConverter.cs` 的转换器第 40 行在读文件（`ResourceFileIo.ReadAllBytesAsync`），第 54-70 行才造 Texture2D/Sprite——**一个转换器同时干了取内容和造对象**。

**病根不在某两行，在接口形状**：`IFileResourceConverter.ConvertAsync(string path, ...)` 的入口是"路径"，等于宣告"转换器自己读文件"；而且两个接口的**输出类型是同一个 `LoadedAsset`**，谁也说不清谁产出了什么。

### 已落地

| 项 | 改动 |
| --- | --- |
| 接口输入输出分开 | 新增 `LoadedContent`（加载的产物：内容 + 释放责任）；`IResourceLoader.LoadAsync` 返回 `LoadedContent`，`IFileResourceConverter.ConvertAsync` **接收 `LoadedContent`、返回 `LoadedAsset`** |
| 转换器不碰文件 | 内置 `BytesFileConverter` / `TextFileConverter` 改为接收已取到的内容；`FileConversion` 收拢"读文件 + 转换异常归类"（原先两个加载器各写一遍） |
| 加载器只取内容 | `LocalFileLoader.LoadAsync` = 读文件；`RemoteFileLoader.LoadAsync` = 落盘后读；转换分别由两者的 `IConvertingLoader.ConvertAsync` 在取到内容之后执行 |
| 编排层不解释内容 | `ResourcePipeline._ConvertAsync` 只问"这个加载器会不会转换"（`IConvertingLoader`），不需要转换的来源（引擎共享对象）直接把内容当资产 |
| Unity 适配 | `ResourcesLoader` 改为交 `LoadedContent`；引擎来源无转换步骤 |

### 过程中发现并修正的两处真实缺陷

1. **退出后不再启动后端，导致"迟到产物"这条保证失去落点**。我在批准提交里加了 `!_isDisposed()`，退出后不再进入后端；于是"后端已在跑、产物迟到"这条路径在退出场景下不可达，原用例 `无人接收的迟到产物由原记录收尾` 因此失效。**这不是纯测试问题**：放弃（最后一人取消）路径仍然需要这条保证。修法是把"记录已被放弃就不交付、但产物仍由本轮释放"写进转换提交，并把用例改为**确定性地经由放弃路径**验证（等待者主动取消 → 记录放弃 → 后端无视取消迟到完成 → 产物被释放且不留下复用项）。
2. **转换失败时"已取到的内容"无人释放**。原来内容就是产物，兜底路径能覆盖；分离后内容是独立对象，转换抛错时它没有主人。修法：`_ConvertAsync` 在转换失败时释放内容，并给出不变量注释——**内容一旦取到就必须有主**。

`ResourceSystem` **67 项通过**、全量 **75 项**、Unity 适配层编译 **0 错误**。另修正一处既有用例的来源写错（`接续尝试下每个请求最多承担一次失败` 注册 Local 却请求 Remote，一直在报 `loader.not_registered`，只是偶发才被断言抓到）。
