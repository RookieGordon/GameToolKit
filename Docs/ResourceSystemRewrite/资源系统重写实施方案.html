资源系统重写实施方案

现行设计，更新于 2026-10-14。资源请求由业务产生，LoadManager 合并同键请求并提交到各加载器自己的异步队列；独立消费者等待任务并执行加载，完成时一次建立各请求的独立持有并通知接收者。已经加载的产物、下载文件、池中实例分别管理。资源容量与回收时机由业务决定；框架检查持有关系、执行显式卸载，把释放失败的具体残留移入独立脏集合。

本文件统一描述现行流程、职责、接口和实现约束。既往多轮方案、卸载职责收紧前方案与独立异步队列改造前方案均保存在历史目录，仅用于追溯，不与本文件叠加执行。

1 需求边界与设计模式

需求 实现边界
统一加载、释放、池化和缓存 业务使用 LoadAsync、RentAsync 及各自凭证；来源显式指定
支持 Resources、AssetBundle、本地、远端 每个 ResourceSource 直接对应一个加载器，不经名称二次映射
用户可替换加载实现 组装时可替换；运行时可新增未注册来源，不支持已有来源热替换
不限制项目目录或清单形式 地址由具体加载器解释；AssetBundle 的包与依赖生命周期由接入方管理
内存回收由业务决定 核心不设置内存容量、估算字节、LRU 或资源 TTL；提供按范围卸载及结果反馈
清理异常隔离具体对象 实际残留进入脏集合，不占正常键索引、不自动重试、不封锁后续请求
远端优先复用本地文件 有效缓存命中直接返回路径，未命中才调用填充方法下载
防止下载文件长期堆积 启动时扫描并按容量目标尽力删除；运行期无定时删除、容量硬上限或文件租约
独立取消与明确失败范围 单个请求取消不取消其他请求；本地共同失败、远端后继继续尝试由注册策略指定
简单且可维护 从流程确定职责；不为模式补空壳，也不把所有动作都包装成队列任务

主协作模型是生产者—消费者：业务产生资源需求，LoadManager 合并同键请求并只为首个请求登记、入队；每个加载器拥有独立 LoaderQueue，消费者空闲时异步等待，有任务时取出并调用该加载器。生产者不领取并发额度，也不启动本次消费。消费者是长期存活的异步循环，不占用等待线程。缓存命中与引用归还直接按职责处理。

同任务的接收者保存在请求列表中，各自等待一份完成通知。成功通知携带独立 ResourceRef，失败、取消和后继尝试按请求分别完成。这是任务级一次性通知，不另建全局事件中心或观察者接口。

辅助采用 GoF 的策略、外观、适配器，与主模型共 4 个：策略用于加载器和转换实现替换；外观由 ResourceManager 提供统一业务入口；适配器把 Unity、第三方资源框架和下载工具接入已有接口。生产者—消费者不属于 GoF 23 种。其他模式不增加独立结构，模式选择服从主流程。

不在当前范围：同步加载、通用场景加载、插件发现与热插拔、严格磁盘配额、内存预算与自动淘汰、AssetBundle 卸载与依赖管理、自动恢复清理故障、等待全部业务归还的管理器关闭协议。

2 主流程与职责

2.1 加载主线

生产者：路由与解析 → 查可复用产物 → 命中即交付，未命中订阅同任务或登记并入队 → 等待自己的通知。

消费者：await 队列通知 → 出队并复查任务 → 调用加载器 → 交付引用或通知失败 → 回到异步等待。

每个业务调用是一份请求，同一身份的多个调用可以订阅一份实际加载任务。调用者只等待自己的结果，不参与消费启动或轮流领取同一产物。查询旧产物失效不会触发释放，不等待旧引用归还；业务明确开始的卸载和已经放弃的原生操作，仍须观察实际结束。图中消费者按有限并发模式表达；不限并发时，由一个循环出队并独立分发每份任务。

2.3 身份与所有权

  • ResourceKey = ResourceSource + ResolvedResource.LocalKey。核心按 Ordinal 比较，不猜路径、不删查询参数、不改小写。影响内容、版本、表示或释放规则的参数必须由加载器纳入身份。
  • ResolvedResource.Payload 仅由选中的加载器解释，作为本次执行快照；不能携带需要核心释放的未交付资源。
  • 成功返回 LoadedAsset 是加载器向框架交出产物管理及约定释放责任的边界。此前失败由加载器回退中间资源，回退失败则在异常中交出具体残留；此后由框架至多调用一次释放回调。未转交所有权的 AssetBundle 资产没有释放回调，框架不因取得资产而推断自己拥有包。
  • 成功完成请求任务是框架向调用者交付引用的边界。先增加持有，再完成任务；成功后发生的取消不能丢弃已经分配的引用。
  • 临时任务在成功交付或失败通知完成后移除。无人接收、无效产物或取消后的迟到产物，必须由原操作完成释放后再退出，不能留给下一次请求补救。
  • ResourceRef<T> 与 InstanceLease<T> 都是非池化的引用类型，Dispose 幂等，释放后的外部凭证永久失效。

2.4 四条完整流程与对象账

以下固定使用已初始化的 Unity 宿主、默认 RemoteFileLoader + SimpleDownloader + BytesFileConverter，业务请求 LoadAsync<byte[]>(url, ResourceSource.Remote)，没有自定义参数、重试或取消；“首次加载”指内存和磁盘均未命中。初始化组装不重复计入每次请求。表按实际职责分类：执行组件、辅助方法、数据记录和每次分配分别列出；BCL 的 Task、TCS、集合、委托、闭包、URI、流、字符串及编译器生成对象不计入自定义类型数量，但不会把它们说成没有分配。实际 byte[] 是资源内容，不是包装。

首次远端加载成功：

ResourceManager.LoadAsync<byte[]>
  → LoadManager.Route / LoadReferenceAsync / _AcquireReferenceAsync
  → RemoteFileLoader.ResolveAsync
      → 默认构造 RemoteFileRequest（FileRequest + DownloadRequest）
      → FileLoadParameters.GetConversionKey(null) 返回 null
      → FileResourceConverters.Get(byte[]) 选定转换器
      → FileKeyEncoding.Encode 组成身份
      → ResolvedResource + RemotePayload
  → IExecutionContext.RunAsync：ResourceStore 查内存
      → 未命中，创建 PendingResourceRequest 和 LoadOperation
      → LoaderQueue.Enqueue
  → LoaderQueue 消费循环 → LoadManager._ConsumeLoadAsync / _RunLoadAsync
  → RemoteFileLoader.LoadAsync → FileCache.GetOrCreateAsync
      → FileKeyEncoding.Encode，查索引、有效期与 File.Exists
      → 未命中，登记 PendingFileWrite；TaskWaitExtensions 等待共享完成
      → fill → DownloadErrorMapping → SimpleDownloader.DownloadAsync
          → DownloadTask.ExecuteDirectAsync（静态）→ HTTP 读取并写入临时文件
      → FileCache 校验临时文件、改名发布、保存 CachedFile、通知等待者
      → 复用本次发布校验；返回普通文件路径
  → BytesFileConverter.ConvertAsync → ResourceFileIo.ReadAllBytesAsync
      → LoadedAsset.FromUnmanaged(byte[])
  → LoadManager 在执行上下文提交结果
      → ResourceStore.AddEntry(ResourceEntry)
      → PendingResourceRequest.CompleteWithResource → ResourceStore.CreateReference

SimpleDownloader 在这条路径调用 DownloadTask 的静态方法，不创建 DownloadTask 实例、不进入旧 AddTask/Start 队列。内置远端加载器目前没有调用传入的进度接口；LoadOperation 实现进度接口是为了支持会上报的加载器，不能把进度分发算作每次成功必经阶段。

类别 这条路径涉及的自定义类型 本次新建情况
长期流程组件，9 种 ResourceManager、LoadManager、ResourceStore、LoaderQueue、RemoteFileLoader、FileResourceConverters、FileCache、SimpleDownloader、BytesFileConverter 组装/注册时已有，本次不各建一份

已有注册与策略记录 LoaderRegistration、LoaderPolicy、NetworkOptions 按组件寿命保存；ResourceSystemOptions、FileCacheOptions 是组装配置输入，构造时读取/复制字段，不算长期保存的中转记录
解析/执行输入，5 个对象 RemoteFileRequest、FileRequest、DownloadRequest、RemotePayload、ResolvedResource 默认每次 Resolve 各建立 1 个
在途记录，3 个对象 PendingResourceRequest<byte[]>、LoadOperation、PendingFileWrite 单调用首次加载各建立 1 个；前两个按内存身份协调，后一个按文件身份协调
缓存与产物记录，3 个对象 CachedFile、LoadedAsset、ResourceEntry 各建立 1 个，分别保存磁盘文件、后端产物契约、共享内存产物事实
每请求凭证，1 个对象 ResourceRef<byte[]> 成功交付建立 1 个；多个请求交付不同凭证

因此这里列出的自定义请求相关类对象为 5 + 3 + 3 + 1 = 12 个，不是“只经过几个核心类”，也不是全部运行时分配的数量。按源码构造点核算，本场景首次加载由 14 → 12，省去空 FileLoadParameters 和 LoadProgressReporter；内存命中由 8 → 6，省去空参数及 PendingResourceRequest，其 TCS 属于另计的 BCL 分配。这不是运行时分配剖析，也不表示 12 层嵌套。异常诊断还会涉及 FileSystemErrorClassifier、LoadError、ResourceLoadException、错误映射器等，未发生异常时不计作本条成功路径的执行步骤。

内存命中：ResourceManager → LoadManager → RemoteFileLoader.ResolveAsync → 执行上下文 → ResourceStore.TryGetEntry / IsLive / CreateReference → ResourceRef。仍会建立上述 5 个解析/执行输入对象；本轮没有把 Resolve 提到缓存之后，因为核心的键由加载器解析决定。命中后只建立新的引用凭证，不创建 PendingResourceRequest、其 TCS、LoadOperation 或 PendingFileWrite，不进消费队列，不访问 FileCache、不下载、不转换。它不是零分配路径。仅磁盘命中、内存未命中时仍需消费加载任务并读取文件转换，只省略下载。

资源凭证归还：ResourceRef.Dispose → 执行上下文 → ResourceStore.ReleaseReference → ResourceEntry.HoldCount--。普通归还的业务类由 ResourceRef → LoadManager → ResourceStore 的 3 个缩成 ResourceRef → ResourceStore 的 2 个，执行上下文仍是线程基础设施。已有 ResourceEntry、LoadedAsset 是所访问的记录，不是两次新的包装。持有归零只变为 Idle，既不卸载 byte[]，也不删除磁盘文件。Value / IsValid / Retain 同样直接查 Store；只有 Retain 建立新的独立凭证。

实例租约归还：InstanceLease.Dispose → IExecutionContext.Post → InstancePool.Return → _ReturnRecord → 工厂 IsAlive / OnReturn → 原 PoolBucket.Idle。这条普通路径执行 InstanceLease、InstancePool、具体工厂 3 个业务类型，并经过执行上下文；PoolBucket 和 InstanceRecord 是已有记录，原型 ResourceRef / ResourceEntry / LoadedAsset 是依赖持有，不在每次归还时再包装。无法缓存时，在同一归还方法末尾进入 _RunDestroyAsync → 工厂 DestroyAsync；回到上下文记账、唤醒等待者、检查桶是否关闭。关闭满足条件才通过原型 ResourceRef → ResourceStore 归还持有。销毁失败才建立脏记录并额外保留原型。归还不创建新租约或实例记录，后续再次租出才创建新的 InstanceLease。

2.5 本轮删减作用在哪一层

原路径/做法 现行路径/做法 实际减少
已交付引用访问、保留、归还经 LoadManager ResourceRef 直接访问 Store 删除已交付阶段的无职责转接；不减少首次加载所需组件
查缓存前创建 PendingResourceRequest 及 TCS 确认需要加入/建立加载后再创建 每次内存命中少 1 个自定义请求对象及其 TCS；等待旧操作时也不提前包装
每个 LoadOperation 配套 LoadProgressReporter LoadOperation 自己实现进度接口 每个实际操作少 1 个代理对象；不是删除一个必经的结果处理阶段
默认文件参数先 new 空 FileLoadParameters 再读取 直接提取可空 ConversionKey 每次默认文件 Resolve 少 1 个空参数对象；业务显式参数契约不变
_ReturnRecord → _ProcessReturnedRecord，再经 _TransferToDestroying 归还判定放一处；不能缓存统一进入 _RunDestroyAsync 并在开头登记 删除 2 个私有方法及其转接，不增加生产类
发布验证后，各等待者重复读取同样校验数据 共享已验证的 CachedFile；仅新增摘要要求或历史命中重新读取 减少重复磁盘操作；FileCache 本身增加必要分支，未因此减行

LoadedAsset → ResourceEntry → ResourceRef 保留三种不同所有权：后端产物和释放契约、多人共享的一份具体记录、单个调用者幂等归还的凭证。合并前两者会把核心计数写入公开后端契约；合并后两者会让一个调用者 Dispose 影响另一个调用者，或迫使外部管理引用标识。它们不是三层重新复制资源内容。完整流程的组件数量没有普遍下降；本轮下降的是明确列出的转接、每请求对象和重复 I/O。

3.2 加载器

public interface IResourceLoader
{
    Task<ResolvedResource> ResolveAsync(ResourceRequest request, CancellationToken cancellationToken);
    Task<LoadedAsset> LoadAsync(ResolvedResource resource,
        IProgress<ResourceProgress> progress, CancellationToken operationToken);
}

// ResourceRequest: Source, Address, RequestedType, Parameters
// ResolvedResource: LocalKey, RepresentationType, Payload
// LoadedAsset: Value, IsAlive, ReleaseAsync
// new LoadedAsset(value, isAlive: ..., releaseAsync: ...)；无底层释放责任时省略 releaseAsync

ResolveAsync 将业务地址解释为身份和执行输入，支持异步查询或加载器自己的清单缓存。它不加载并交出最终对象。LoadAsync 接收整个操作的独立取消令牌，不能把首个请求的个人令牌用作共享加载生命周期。

LoadedAsset.IsAlive 是无副作用的存活查询；Unity 实现使用 Unity 对象的存活语义。ReleaseAsync 按产物拥有者的释放契约完成。Unity 图片转换器的 Destroy 正常返回表示销毁请求已接受，不能因帧末之前仍存活就误报失败；GameObject 实例工厂仍等待实际销毁，以保护实例依赖的原型。第三方资产如何释放不由核心根据类型猜测。

同键必须提供兼容的产物与释放语义。释放回调只处理它捕获的具体对象，不按地址重新查找后来的产物。Resources 的失败旧对象可能在后续请求中重新取得，因此脏集合不得自动重试卸载。AssetBundle 生命周期由外部所有者处理，不加入核心释放故障判断。

5 加载算法与时序

5.1 缓存查询与请求登记

缓存查询、命中时增加持有、未命中时登记请求在同一次执行上下文提交中完成，不能先查再在另一次提交里登记。加载前不扫描脏集合，也不负责清理旧资源。

发现的事实 本次动作
存在有效产物 验证请求类型，创建独立引用，直接完成
旧产物失效 标记具体记录失效，撤下当前复用索引，继续新加载；旧引用仍绑定原对象
业务已经开始卸载当前产物 等待其 RemovalTask 真实完成，再重新查询；释放失败同样解除等待
旧加载已放弃，实际操作仍未收尾 等待 Finished，新请求不加入
已有可加入的 LoadOperation 只添加本请求
没有可复用产物、没有加载 建立任务并放到该来源的 FIFO 队列

普通加载在必要等待结束后重新 Resolve，允许版本已改变；池原型使用建桶时固定的 ResolvedResource。旧记录脱离复用索引后仍在具体产物集合中，等业务卸载；旧卸载完成只能移除旧记录，不能误删后来登记的同键产物。

5.2 独立消费与任务通知

每次加载器注册都会创建自己的队列和消费循环。MaxConcurrentLoads 默认 4：正数对应固定数量的消费者，每个消费者一次只执行一份任务，完成本轮交付或收尾后再取下一份。0 保留不限制并发的约定：一个分发循环持续出队，每份任务独立异步执行。不同加载器的队列和消费者互不占用对方的等待位置。

队列空闲时使用 SemaphoreSlim.WaitAsync 等待到达信号，不轮询、不阻塞线程。入队只入 FIFO 并发送信号；不会在生产者的调用栈中执行加载。消费开始前使用异步交接，切断之前的同步完成或取消回调栈，再交给 LoadManager 复查任务并执行。该队列不提供专属线程、全局优先级、严格消费完成顺序或持久化任务保证；FIFO 表示出队顺序，异步任务的结束顺序可以不同。

同键实际加载由临时任务登记协调：任务尚可加入时，新请求只加入其接收者列表；每个请求有自己的完成通知，成功分配独立引用后才通知。资源本地/远端的失败范围仍由注册策略决定。当前产物可直接复用；失效旧对象从复用索引分离后允许出现同键新对象，两者以具体记录区分。不再叠加同键资源锁，通用 KeyedAsyncLock 继续供其他模块使用。

RegisterLoader(source, loader, policy):
    创建 LoaderRegistration 与独立 LoaderQueue
    有限并发 → 启动固定数量的异步消费者
    不限并发 → 启动一个异步分发循环
    各循环首先 await 队列通知

    异步交接，离开生产者或前一回调的同步调用栈

        已经终结 → 跳过旧队列项

成功通知之后不能再加一层“可取消等待”而丢掉已交付的引用。交付阶段不重新解析、不清理上一轮对象，也不自动重载；每个请求的类型不兼容只使该请求失败，不阻止其他兼容请求取得引用。接收者订阅的是本任务的一次结果，不需要跨任务取消订阅或维护永久回调表。

5.3 失败、重试与全部放弃

条件 请求完成方式
FailWaitingRequests 同轮仍在等待的请求共同失败；后续新请求可重新尝试
ContinueWaitingRequests 发起本轮尝试的请求失败；其他未取消请求收到重试信号，重新解析后合并下一轮
清理失败且带有实际残留 先记录脏对象，再按本轮失败策略通知；不永久封锁同键
仅有 Unknown 或 Incomplete 标记，没有实际残留 保留错误诊断，不制造空脏对象，不改变后续准入
单个请求取消或超时 只移除此请求；其余请求仍可接收本轮结果
所有请求放弃且尚未执行后端 立即结束通知并移除任务登记；旧队列项以后被取到时跳过，不调用加载器
所有请求放弃且任务已执行 取消操作令牌，保留该操作直到后端真实结束，释放迟到结果

失败策略由注册配置决定，核心不根据 Local/Remote 名字推断。Unity 宿主注册远端文件加载器时明确使用 ContinueWaitingRequests；单独注册时应显式设置所需策略。这里的后继尝试不代表自动无限重试原失败请求，也不把 Resources 加载失败直接解释为资源文件损坏。

取消分为两步：上下文内移除请求并标记操作放弃；离开提交委托后才通知底层取消令牌。取消回调可能让加载立即同步完成，不能把它当成不会执行外部逻辑的字段赋值。退出时也遵循这一顺序。

6 引用、缓存与业务卸载

6.1 归还与保留

ResourceStore 管“存着哪些具体对象、谁还在用”，业务管“还要不要留着”。最后一个引用归还只把记录改为 Idle；核心不按容量、时间或估算字节自动卸载。Tick 只维护实例池。下载文件的启动清理保持独立，不因为内存策略收缩而改变。

ResourceRef 直接持有 Store 及具体 Entry。Value / IsValid / Retain / Dispose 不经过 LoadManager；Store 使用同一个执行上下文串行访问记录。首次交付由加载流程先确认产物有效，CreateReference 只检查类型并增加持有，不再重复调用底层存活判断。Retain 在新建持有前查存活；清理失败残留所依赖的原型使用内部 AddReference 保留，不能以再次存活检查失败为由丢失残留所有权。

Loading / Draining 来自临时任务的诊断投影。Dirty 是独立集合，不是 ResourceState 值，也不参与后续加载准入。产物失效只撤下复用索引，不触发上图的 Unloading；仍保留原条目和引用，直到业务卸载或进程退出。

ResourceRef.Dispose:
    外部凭证原子置为已释放，重复调用结束
    当前已在执行上下文 → 直接 Store.ReleaseReference(具体条目)
    其他线程 → Post 回上下文，再 Store.ReleaseReference

    只减少这份条目的持有，不查加载操作、不按 key 寻找替代产物

    回到上下文，逐个复查当前引用数量:
        已移除 → 跳过

        无人持有 → 标记 Unloading，登记本次释放

6.2 业务调用与失败隔离

归还不等于卸载。 真正释放由业务 ResourceManager.UnloadUnusedAsync → LoadManager.UnloadUnusedAsync → LoadedAsset.ReleaseAsync → 后端/转换器捕获的释放回调 执行，随后 LoadManager 移除具体 Entry 或记录残留。保留“快照 → 在状态提交外运行选择器 → 回上下文复查持有 → 发起释放”的顺序，因为选择器可能重入加载并重新持有资源；删除复查会卸载刚被业务取得的产物。普通引用归还不走这段编排。

// 退出玩法后先结束实例使用，再归还资源持有，最后选择本次卸载范围。
lease.Dispose();
await resources.ClearPoolAsync("enemy", ResourceSource.AssetBundle, cancellationToken: ct);
var result = await resources.UnloadUnusedAsync(
    row => row.Key.Source == ResourceSource.Remote,
    cancellationToken: ct);
// result.ReleasedCount / result.SkippedInUseCount / result.Failures
var leftovers = resources.GetSnapshot().DirtyResources;

在 Unity 主线程连续调用 reference.Dispose() 和 UnloadUnusedAsync() 时，归还立即记账，本次卸载能看到引用已归零；其他线程的归还通过执行上下文投递。业务选择器不在内部状态提交中运行；它可能重新取得资源，故卸载前必须再次检查引用。选择器只决定本次范围，不成为常驻的内存策略注册点。释放某项失败不阻止其他已选项完成；重复卸载调用可以观察同一实际释放的结果，不重复启动回调。

脏集合保存明确失败的旧对象及诊断，不自动修复。若异常没有显式 CleanupRemainders，释放阶段保留 LoadedAsset 及其值，以免丢掉释放回调闭包中仍被持有的 native 对象；不会再次调用该回调。转换器能指出具体失败对象时，只保留这些对象。保留残留会继续占用内存，这是隔离的代价，不能描述成已经回收成功。

Resources 卸载失败不等于加载失败；后续可能取得相同底层对象。因此绝不能由脏集合后台重试旧卸载。转换器每次创建独立的 Texture/Sprite，旧对象清理失败后可以继续创建新对象。框架不处理 AssetBundle 卸载结果。

7.2 实例与原型保护

实例记录只保留对象、租约标识和归还时间；Idle 队列与 Active 表直接表达实例归属。等待者是否已交付、失败或取消由 Completion.Task 的终态表达。InstanceLease 自己的一次性归还标记使旧租约不能重新生效。

InstanceLease.Dispose 保留始终 Post 的时序，不采用 ResourceRef 的同上下文立即归还。现有 InstanceAutoReturn.OnDestroy → lease.Dispose 会在销毁回调里归还，而 Unity 将 OnDestroy 定义为对象或组件即将销毁时的通知；此时不能仅凭工厂的 Unity 存活判断就立即执行 OnReturn 并交给新租用者。因此本轮保持归还离开该回调栈的边界，不引入一套自动归还专用协议。Unity OnDestroy 文档。这是基于现有调用链与引擎生命周期约束的保留依据，本轮未做真实 PlayMode 时序复现。

Idle / Active 中仍有实例，或 Preparing / Returning / Creating / Destroying 仍有在途工作时，原型都不能提前归还。在途计数保护的是回调与异步操作期间的所有权，不能用集合数量替代。创建和销毁要观察到真实结束；取消后的迟到实例必须销毁或按合法归还流程处理。存活查询异常不等于确认对象已销毁。

每桶等待者按 FIFO 处理，每桶同时最多一次创建；活跃配额统计 Active + Preparing + Creating。空闲实例超量或到期销毁。ClearPoolAsync 捕获当时与 (source, address, factory) 关联的全部桶代际，关闭后拒绝这些桶的新租用；新租用可创建新代际，旧租约始终归还原桶。

PoolState 的 Closing/Closed 是具体池桶的局部关闭过程，与管理器生命周期不同。销毁失败只隔离对应实例，不封锁整个 PoolKey；当前池与后续同键池仍可继续创建、租用。

残留实例可能依赖原型，脏记录因此保留一份独立原型引用。这个引用使业务卸载跳过仍被残留依赖的原型，避免通过“隔离”掩盖提前释放。池内没有失败对象充当活跃或闲置实例。关闭过程中发生的失败汇总到 CloseError；ClearPoolAsync 等初始化、创建、销毁和旧租约归还实际结束后，才返回关闭结果或抛出清理异常。以前已经隔离的失败不成为未来租用或新池的故障屏障。

7.3 业务绑定

ResourceScope 持有调用者交入的凭证并按逆序释放。ResourceBinder 以目标引用及 slot 为键，后发请求替代同 slot 的未完成请求；新资源应用成功后才释放旧持有。取消或失败保留旧显示，主动 Revert 先清除目标属性再释放引用。

每次绑定申请持有独立的内部取消源。登记新申请后取消旧源；申请交付前检查自己的取消源，即可知道是否已被取代。取消源同时承担停止旧等待与记录过期的作用，不再增加绑定代际号。调用者自己的取消仍按用户取消处理，被后发申请取代返回 Superseded。

Apply(target, slot, request):
    准备本次内部取消源
    try:
        上下文内登记本次申请，再通知旧申请取消
        关联用户令牌与内部令牌，等待资源引用
        回上下文：本次内部源已取消 → Superseded
                  否则 Replace 成功后替换 CurrentRef，再释放旧引用
    finally:
        已登记且 PendingWaiter 仍指向本申请 → 移除本次登记
        释放未交付候选；登记阶段异常也执行同一收尾

绑定表的读写由同一执行上下文串行化，没有另一层 slot 锁。Mutating 只在 Replace/Revert 同步回调期间拒绝同 slot 重入修改。IResourceApplicator.Replace 要求异常安全：失败时原属性保持原状；Revert 清除成功后才释放引用。InstanceAutoReturn 仅作为实例租约的自动归还便利层，不创建另一套引用机制。

8.1 缓存与 HTTP 解耦

Task<string> FileCache.GetOrCreateAsync(
    FileRequest request,
    Func<string, CancellationToken, Task> fill,
    CancellationToken cancellationToken = default);

// FileRequest: FileIdentity + FileValidity + 可选长度/SHA256
// FileCacheOptions: Directory + StartupTargetBytes
// RemoteFileRequest: Cache(FileRequest) + Download(DownloadRequest)

FileCache 不引用 URL、请求头或下载错误类型。RemoteFileLoader 将文件请求与下载委托组合；默认复用项目 SimpleDownloader.DownloadAsync，HTTP 重试、连接并发和网络超时留在下载工具中，一次共享填充只调用一次 fill。

启动扫描只读文件名、长度等元信息建立路径索引，不把目录里的文件内容全部加载到内存。每次复用仍检查 File.Exists 及有效期；源文件在运行期被外部删除时不能仅凭启动索引认定命中。

8.2 文件生命周期

InitializeFileCache:
    创建专用目录
    扫描本缓存识别的完整文件及临时文件
    删除识别出的临时残留和同身份旧副本
    按完成时间从旧到新尽力删除，直到 StartupTargetBytes 目标
    为保留的最新完整文件建立路径索引

GetOrCreate(fileRequest, fill, callerToken):
    未完成初始化 → 明确失败，不等待隐藏初始化
    短锁内:
        校验同身份的有效期约定
        有效路径 → 复用候选
        有填充 → 加入共享完成任务
        否则 → 登记一次填充
    只有本次新登记的填充在锁外启动 fill
    未命中时等待共享完成；个人取消不取消实际填充
    历史缓存命中 → 按本调用者声明重新校验文件
    本轮填充结果:
        加入者新增发布者未声明的摘要 → 读取文件验证增强声明
        否则 → 复用发布校验，用记录的实际长度检查本请求长度要求
    已命中记录校验失败 → 只撤下仍指向该文件的索引，保留旧路径
    返回完整路径

FillAndPublish:
    await fill
    按发起填充的请求验证临时文件，取得实际长度
    同目录改名为唯一完整路径，用 CachedFile 更新索引
    清理未发布的临时文件
    移除进行中的填充，以同一 CachedFile 通知全部等待者

文件名由身份摘要、完成时间及随机标识组成；只处理缓存认识的名称，不递归删除业务目录。调用方应为每个活动缓存实例分配独占专用目录，当前没有跨进程目录锁协议。

运行期不删除已交付的完整路径，因此无需文件租约。到期或校验失效后，新填充发布到新路径；旧路径留到下次启动清理。允许运行期超过启动容量目标，真正写满磁盘时报告本地存储故障并尽力删除临时文件。启动删除失败报告诊断，容量目标不是严格保证。

同文件身份为 Namespace + ArtifactId + Revision + Variant，与内存目标类型和转换参数分离。不同内容权限上下文必须使用不同身份。有效期为 Immutable 或 ExpiresAfter；同一身份不允许混用冲突的规则。

同一共享填充在登记时检查加入请求与发起请求之间冲突的长度或摘要声明。内部完成通知从路径改为已有 CachedFile，没有新增“校验凭证”类型；公开接口仍返回 string 路径。只对本次填充复用已经验证的事实，历史命中仍重新检查文件，不能声称以后永远不用读盘。

条件 本轮前 现行行为
发布者声明 SHA256，N 个等待调用的要求已被它覆盖（N 包含发起者） 发布 1 次，加各调用交付前 N 次，共 1+N 次全文件摘要扫描 本次发布 1 次；各调用复用结果
发布者无 SHA256，各调用也没有摘要要求 重复读取 FileInfo/检查长度；没有全文件摘要扫描 发布时取得长度，交付时比较记录的长度
发布者无 SHA256，加入者新增摘要要求 加入者独立验证 仍由加入者读取验证，失败只影响该声明，不撤销已发布文件
历史磁盘缓存命中 按本次请求声明检查文件 保留；File.Exists、有效期和所声明的内容校验仍执行

8.3 远端身份与转换

默认远端身份保留影响内容的端口和查询参数；无显式版本时默认 24 小时 TTL。若签名 URL 不同但内容相同，业务提供稳定身份的 requestBuilder 才能共享文件，核心不擅自删除鉴权或查询参数。

内存身份同时包含源文件身份、精确目标类型与 FileLoadParameters.ConversionKey。同一文件可转换为多个独立表示。默认转换表注册 byte[]、string；Unity 组装同一个图片转换器为 Texture2D 与 Sprite。转换器在 Resolve 时选定并放入本轮 Payload，加载时不二次路由。

转换失败不自动证明文件损坏，不删除下载缓存。ConversionKey 由具体转换器解释并进入内存身份；当前内置转换器使用固定转换行为，不把该字符串当转换器名称。

文件缓存、字节/文本转换和 Unity 图片转换共用 FileSystemErrorClassifier 的文件错误分类，保留原始原因、路径和阶段；网络错误仍在下载接入处映射。字节读取通过 FileStream.CopyToAsync 完成，不再维护手写异步复制循环。

    Task.FromResult(new BundleLocation(

Unity 原生加载请求一旦启动，就观察到实际完成。完成回调已在主线程，因此 Resources 与 AssetBundle 加载器在该回调中检查原生结果并构造 LoadedAsset，直接交给核心，不再先传出原生对象再投递一次主线程检查。已同步完成的原生请求走同一结果读取逻辑。

10 线程、初始化与退出

10.1 执行边界

状态变更在一个 IExecutionContext 内串行提交。Unity 实现绑定主线程，RunAsync 跨线程时返回可等待任务，不使用 ManualResetEventSlim 阻塞等待。加载器路由使用自己的短同步锁，查询不投递主线程，锁内不调用加载器。

LoadAsync/RentAsync 生产路径只登记接收者和入队，后端由各加载器的独立消费循环执行。池登记仍返回初始化责任，固定原型的获取复用同一生产入口。ConfigureAwait(false) 不保证切线程，RunAsync 在当前上下文也可内联；异步消费者不是新增专属线程。

队列到达信号与消费开始的异步交接，使加载器不嵌入生产者或前一后端同步完成/取消的调用栈。消费者在执行上下文内只复查并登记开始，随后离开提交调用加载器。Unity API 的线程要求由具体适配器负责；这些条件不等同于保证别的线程已经离开所有状态提交。

工厂、存活查询与部分通知本来就可能在上下文内运行，允许的同步重入按各模块的状态复查处理。当前没有提供“任何外部回调重入的新请求都延后至最外层提交退出”的通用调度保证，不能把直接入口的验证扩大为该保证。

操作 Unity 调用要求
LoadAsync、RentAsync、UnloadUnusedAsync、ClearPoolAsync 可任意线程发起，状态提交返回上下文
注册、InitializeAsync 发起、Tick、GetSnapshot 主线程
ResourceRef/InstanceLease 的 Value、IsValid，以及 Retain 在执行上下文访问
凭证 Dispose、管理器 Dispose 幂等，可任意线程调用，必要时投递
Unity 对象创建、存活判断、应用、销毁 由对应集成实现回到主线程

10.2 统一初始化

InitializeAsync(configure, callerToken):
    登记唯一初始化完成任务
    首次调用执行 configure
    await 注入的共享 FileCache.InitializeAsync
    再检查 Dispose，成功后开放业务入口
    重复无 configure 的调用等待同一任务

个人取消只取消这次初始化等待，不撤销其他调用者的共享初始化；再次提供 configure 报错。初始化失败保持失败事实，不把下一个资源请求变成重试初始化入口。配置在构造或注册时复制为快照，修改原 options 不热更新系统。

10.3 进程退出释放

资源管理器跟随游戏进程运行，只有 IsInitialized 与 IsDisposed 两个独立事实，不以资源是否全部归还或某次异常来改变全局服务状态。

Dispose 立即拒绝新请求、作废凭证并发起释放，不阻塞主线程、不等待业务归还。先通知待加载请求并停止各加载器队列，再等待实际实例创建/销毁收尾，随后释放资源产物；迟到加载结果由其原操作清理。产物退出先在上下文登记待释放记录，离开状态提交后调用释放回调；池的 Closed 在实际操作收尾后才完成，不再维护另一份退出完成信号。局部失败进入脏集合并报告诊断，不阻止无关资源；显式卸载和进程退出都不重新尝试旧脏对象。

停止队列只清空待消费项并唤醒空闲消费者退出，不等待业务归还。已经执行的加载仍负责实际结束和迟到产物；有限消费者在本轮完成后退出，不限并发的已分发任务独立收尾。全部队列循环退出后才释放到达信号。组装期替换加载器时停止旧空队列，不引入运行期热替换。

文件缓存仍由创建方负责最终释放。Unity 宿主先发起管理器 Dispose，独立等待缓存实际填充及临时文件清理结束，再释放下载器。进程可以在异步操作结束前终止，IsDisposed 不表示所有 native 释放已经完成，框架不虚构退出完成保证。
