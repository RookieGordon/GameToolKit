## D01 把简单需求升级成更强保证

- **原需求与来源：**下载文件可本地复用，避免长期堆积。用户纠正：“只是为了不让大量的http下载的文件撑爆用户沙盒目录”。之后进一步选择“启动的时候检查一次就行”。
- **错误假设与后果：**方案曾扩展为严格容量预留、临时文件记账、文件租约与恢复协议，并让文件组件承担 HTTP 相关职责。[旧设计中的文件租约与传输职责](D:/Workspace/Porjects/GameToolKit/Docs/ResourceSystemRewrite/历史/资源系统重写实施方案_2026-10-13重构前.md:1674)。增加了大量状态和协作要求，偏离原本控制长期占用的目的。错误在于未经需求依据提高保证，不在于这些技术本身无用。
- **纠正与检查：**先说清容量是启动清理目标还是实时硬上限，文件在何时允许删除；再推导必要流程。文件复用与存储负责文件，下载实现负责传输。若运行期不删除已交付文件，就重新评估运行期占用保护的必要性。
- **边界与状态：**历史设计已被用户要求简化、解耦。启动清理是后来明确的选择，不能倒推此前所有定时清理都属于错误。若其他场景明确要求硬上限、运行期淘汰或恢复保证，仍应实现相应机制。

## D02 套用不符合使用场景的生命周期

- **情境与来源：**资源系统随游戏进程运行。用户后来明确：“可以有dispose流程，跟随主进程一起结束，但是一般只用于释放native资源”。
- **偏差与后果：**此前设计了等待引用归还的关闭流程，以及管理器级 Closing、Closed、Faulted 等状态，使服务生命周期与业务引用、局部清理结果挂钩。用户明确进程生命周期后，这些额外语义需要整体收缩。
- **纠正与检查：**先问实际是否存在独立停止、重启、排空的使用流程。退出清理、资源释放失败、业务仍在持有分别是什么事实，是否真要上升为服务状态？不要仅因“有 Dispose”推导完整关闭协议。
- **边界与状态：**记录的是本项目的边界纠正，不追溯成此前已违反尚未明确的需求。资源管理器已按该方向调整；具体实例池仍可能需要局部关闭与晚归还处理，不能一并删除。

## D03 用关键词和“统一”制造额外概念

- **原需求与来源：**用户可以实现、替换来源加载器；业务明确指定来源。用户纠正：“这里的加载器是可以由用户实现并替换的”，以及“既然ResourceSource枚举已经关联加载器类型了，为啥还要个_sourceLoaders转接到_loaders”。
- **错误假设与后果：**把“插件”扩大为额外体系的设计话语，把“统一入口”理解为需要默认来源、默认加载器，并保留“来源 → 名称 → 加载器”的间接关系。让接入者理解并维护本不需要的概念。
- **纠正与检查：**列出实际需要替换的行为和选择它的业务参数，优先直接关联。任何默认值、兼容入口、额外标识都要指出真实消费者。AssetBundle 的目录、清单结构和依赖处理是否泄漏到公共契约，也要单独核查。
- **边界与状态：**历史接口已做相应收紧。其他项目若确有多个命名实例、默认选择或已发布接口兼容需求，可以保留；本条不禁止插件机制和默认值。

## D04 把局部状态和职责堆在一起，再要求读者自己拼流程

- **情境与来源：**用户能读懂入口，沿 `ResourceStore.JoinOrAcquire` 却失去方向，指出 `Deliver/Barrier` 等名称不知所指；随后追问：“共享资源及其引用应该只是一个容器，为什么要处理加载/下载/排队安排这种事情？”
- **错误判断与后果：**实现曾让资源容器承担编排，通过内部结果分支、标志和相互回调维持行为；把分支齐全、注释充分当成设计清楚。读者必须先理解细节才能知道流程，又必须知道流程才有方向读细节。

## D05 把对象拆分当成所有权边界已经清楚

- **情境与来源：**用户选择临时加载上下文与长期产物分离。前次对照审查发现，结果发布后由 `LoadContext.DeliveryResource` 暂管，零引用释放判断还要反查加载表，最后等待者退出才结束保护。[发布依据](D:/Workspace/Porjects/GameToolKit/Unity/Assets/ToolKit/Tools/Common/ResourceSystem/Core/LoadManager.cs:494)、[释放依据](D:/Workspace/Porjects/GameToolKit/Unity/Assets/ToolKit/Tools/Common/ResourceSystem/Core/LoadManager.cs:598)。
- **判断不足与后果：**完成字段迁移后，过早认为生命周期边界已经收紧；“加载成功、尚未交付”这一阶段的责任仍需跨多个方法才能解释。增加理解成本，不等于已经证实发生提前释放。
- **纠正与检查：**先明确结果产生、暂管、交付、无人接收和释放分别由谁负责，再决定对象结构。任何时候都应能解释谁保护尚未领取的产物，何时交接，全部请求退出后由谁收尾。
- **边界与状态：**属于该次静态结构审查，记录建立时尚未修复或验证。临时/长期分离是用户选择；不能将它记录为错误，也不能为消除反查而删掉必要保护。跨记录关联可以合理存在。
- **2026-10-13 修复与验证：**本轮在成功提交中为全部未取消且类型匹配的请求创建独立引用，再完成各请求并移除临时 `LoadOperation`；删除 `DeliveryResource`、逐个 Claim 和零引用释放时的加载表反查。无人接收或无效的本轮产物仍由原操作释放完毕后退出。相关回归 196/196 通过，其中 [ResourceAcquisitionFlowTests](D:/Workspace/Porjects/GameToolKit/ToolKit/Tests/ResourceSystem/ResourceAcquisitionFlowTests.cs) 覆盖混合类型交付与交付前取消，[ProducerConsumerLoadTests](D:/Workspace/Porjects/GameToolKit/ToolKit/Tests/ResourceSystem/ProducerConsumerLoadTests.cs) 覆盖队列及共享行为。测试证明这些行为，不能单独证明所有结构都已最简。
- **2026-10-13 卸载职责收紧：**用户新明确由业务决定回收时机，失效产物只撤下复用索引，不由后续加载触发卸载。原引用继续绑定旧对象；新对象可以使用同一资源 key，旧卸载完成只移除旧记录。释放失败的具体残留进入独立 `DirtyResource`，转换回退通过 `CleanupRemainders` 交出实际对象。池中失败实例同时保留独立原型引用，不以隔离为由提前归还依赖。这是本轮新增边界，不追溯认定原先等待旧产物退出的约定有误。检查点：晚归还、旧清理完成、同键新产物与残留原型保护必须分别按对象身份验证。

## D06 让复用的工具反过来决定共享流程

- **情境与来源：**用户建议复用 `KeyedAsyncLock` 编排同资源请求，并按场景区分失败传播。审查时每个等待者同时进入锁队列与参与请求列表；成功后，后继请求仍逐个取锁领取同一产物。[依据](D:/Workspace/Porjects/GameToolKit/Unity/Assets/ToolKit/Tools/Common/ResourceSystem/Core/LoadManager.cs:213)。
- **判断不足与后果：**把“已经接入现有协程锁”当作编排简化的证明。执行互斥、参与者取消和成功交付仍形成交叉协议；维护者要同时理解工具阶段与加载流程。
- **纠正与检查：**先说明谁执行一次、哪些请求等待同次结果、个人取消的影响、失败后哪些请求可再尝试，再确定锁或通知负责哪部分。多份记录若职责不同应说明关系；工具复用后要看整条流程是否真的减少了理解负担。
- **边界与状态：**这是静态设计取舍审查，不是“串行领取必然错误”的定论。不禁止协程锁，也不强制广播式实现。独立取消、失败范围和底层实际完成前的保护仍须保留。
- **2026-10-13 修复与验证：**本轮改成每来源 FIFO 实际任务队列与消费者并发数量，同键只登记一份任务；业务请求等待自己的完成通知。加载/产物/卸载阶段记录已保证同键互斥，因此移除 `LoadManager` 内重复的资源锁，不修改通用 `KeyedAsyncLock`。成功批量交付后消费者才接续下一任务；本地共同失败、远端后继重新解析、清理未知隔离和个人取消继续保留。196 项相关回归通过，包括 [ConcurrentLoadPolicyTests](D:/Workspace/Porjects/GameToolKit/ToolKit/Tests/ResourceSystem/ConcurrentLoadPolicyTests.cs) 与 [ProducerConsumerLoadTests](D:/Workspace/Porjects/GameToolKit/ToolKit/Tests/ResourceSystem/ProducerConsumerLoadTests.cs)。
- **2026-10-13 卸载职责收紧：**用户取消按 key 的清理失败封锁约定。删除加载清理故障表和永久失败条目，正常加载不查询脏集合；Unknown/Incomplete 只保留诊断，不改变本地共同失败或远端后继尝试策略。已经开始的实际卸载或放弃后的底层任务仍需等待结束，成功失败都解除协调，不把“发生过失败”等同于“还有操作正在执行”。来源消费者队列和独立取消继续保留；这是用户新要求带来的契约变化。
- **2026-10-13 独立消费循环：**用户进一步明确每个加载器应有自己的异步消费队列：生产者只合并同键接收者并入队；消费者空队列时 await，有任务自行消费。上一轮 `PendingLoads/ActiveLoads` 虽然形成队列与并发限制，生产入口仍承担取任务和启动消费，未表达这次明确要求的独立循环。现改为 [LoaderQueue](D:/Workspace/Porjects/GameToolKit/Unity/Assets/ToolKit/Tools/Common/ResourceSystem/Core/LoaderQueue.cs)，正数配置建立固定消费者，0 保留不限分发；同任务使用既有每请求完成通知，不为“观察者”另造全局事件中心。这是本项目本轮选择，不推导所有生产者—消费者实现都必须常驻；检查生产者不再执行取件/启动、空队列能够重新唤醒、来源互不占用等待位置、排队取消项被跳过以及停止时实际操作仍有所有者。本轮相关回归 208/208 通过、0 跳过，实际 Unity DLL 适配层编译 0 错误；没有运行真实 PlayMode，也不将加载队列的调用栈边界推广到所有实例工厂回调。

## D07 用局部异步边界证明整条调用链安全

- **情境与来源：**优化线程交错时，将加载器调用移出 LoadManager 自己的状态提交块。之后追踪发现，`RentAsync` 可在外层状态提交中调用池初始化；中间等待同步完成时，仍可在外层提交返回前进入加载器。[外层入口](D:/Workspace/Porjects/GameToolKit/Unity/Assets/ToolKit/Tools/Common/ResourceSystem/ResourceManager.cs:359)、[池内启动](D:/Workspace/Porjects/GameToolKit/Unity/Assets/ToolKit/Tools/Common/ResourceSystem/Instancing/InstancePool.cs:200)。
- **错误判断与后果：**把“已移出本方法的提交块”当成外部调用边界成立的依据，没有验证模块组合。带来同步重入与边界不一致风险；该次审查没有证明已经死锁。
- **纠正与检查：**从每个实际公共入口追到底层调用，检查外层是否仍在修改状态，覆盖真正挂起和同步完成两条路径。区分“在主线程执行”与“嵌套在状态修改中”；`async`、`ConfigureAwait(false)` 都不能单独证明离开了当前调用栈。
- **边界与状态：**静态确认的边界问题，记录建立时尚未修复。不要用统一 Task.Run 或同步阻塞修补；具体执行模型服从线程契约和外部 API 要求。
- **2026-10-13 修复与验证：**直接 Rent 入口将池登记与原型初始化启动分开；取消流程先在上下文标记/移除，后在提交之外通知后端取消；消费者接续下一任务时 `await Task.Yield()`，切断旧后端同步完成/取消回调的调用栈。[RentStartBoundaryTests](D:/Workspace/Porjects/GameToolKit/ToolKit/Tests/ResourceSystem/RentStartBoundaryTests.cs) 覆盖同步/异步完成与登记后取消/退出，[ConsumerCancellationBoundaryTests](D:/Workspace/Porjects/GameToolKit/ToolKit/Tests/ResourceSystem/ConsumerCancellationBoundaryTests.cs) 覆盖取消及 ClearPool 续接。相关 .NET 回归 196/196 通过，Unity 适配层编译 0 错误；未做真实 Unity PlayMode 验证，也不据此承诺所有第三方回调重入的新请求都处于最外层状态提交之外。
- **2026-10-13 异步消费边界复查：**独立消费者通过到达信号等待，出队后异步交接，再回执行上下文复查取消/退出并登记开始；离开提交才调用具体后端。检查同步完成、取消回调与同键共享通知时，应观察真正的后台开始事件，而不是把生产请求已返回 Task 当成后端已经执行。测试中的并发峰值必须先等足量后端实际进入，再解除等待，不能让计时假设替代调度契约。

## D08 暴露完整策略，却只兑现部分配置

- **情境与来源：**用户要求配置丰富但不复杂。加载器级 `MemoryPolicy` 暴露 TTL、条目数量和字节预算；审查时，数量与字节淘汰只读取全局配置，加载器数量仅用于判断是否为零。[配置](D:/Workspace/Porjects/GameToolKit/Unity/Assets/ToolKit/Tools/Common/ResourceSystem/Definition/ResourceOptions.cs:110)、[执行](D:/Workspace/Porjects/GameToolKit/Unity/Assets/ToolKit/Tools/Common/ResourceSystem/Core/LoadManager.cs:681)。
- **错误设计与后果：**因为字段形状相同就复用配置类型，却未统一作用范围。给某加载器设置数量为 2 或独立字节预算，并不会得到入口暗示的限制效果。
- **纠正与检查：**每个字段说明限制哪个集合、谁统计、何时执行、覆盖关系是什么。取一个非默认值，沿流程确认其效果。已承诺的能力要兑现；未承诺且不需要的字段应收缩，不能只加注释解释其不生效。
