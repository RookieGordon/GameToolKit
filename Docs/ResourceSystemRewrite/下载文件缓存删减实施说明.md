# 下载文件缓存删减实施说明

本文可直接交给实施代理执行。目标是把 ResourceSystem/Files 收缩为轻量下载缓存：**本地有有效文件就复用，没有就下载；应用启动前清理一次，运行期间不自动清理已完成文件。**

本说明取代原《资源系统重写实施方案》中第 10 章的重型文件管理流程，以及第 9、14、15 章与其对应的配置和验收要求。旧 Review 中要求补齐严格容量、文件 pin、元数据事务的条目，不再作为本次实现目标。资源引用、实例池、AB 容器、错误分层等其余设计继续有效。

实施基准为当前工作区，参考提交 0d33293。不要按旧 Review 的行号恢复已经修正的代码。本文只规定 Files 及其必要调用方的删减，不要求重写整个资源系统。

## 1 已确定的设计边界

1. 清理只在应用启动、任何资源开始加载之前执行一次。切换场景、重建 ResourceManager、完成下载、缓存超量、Shutdown 都不触发已完成文件清理。
2. 本次运行不承诺磁盘容量硬上限。容量阈值只决定启动时尝试保留多少文件；删除失败或本次运行继续下载，都可以使占用超过这个值。
3. 已返回的缓存文件路径，在本次应用运行内不被本组件删除或覆盖。调用者无须取得文件租约，也无须归还文件。
4. 缓存过期与文件删除是两件事。运行期可以因 TTL 到期重新下载，但使用新物理路径，旧路径留到下一次启动处理。
5. 只管理配置的专用缓存目录。业务本地文件、导出文件、第三方 SDK 自有缓存、整个 Unity persistentDataPath 都不属于清理范围。
6. 不建设通用文件系统、跨进程共享缓存、容量预留器、事务恢复引擎或通用缓存策略框架。

这些边界是主动删减后的产品语义，不是临时省略。实施时不要以“完整性”为由加回运行期回收。

## 2 从流程确定职责

### 应用启动

~~~text
装配根创建应用级 FileCache
→ InitializeAsync 扫描专用缓存目录
→ 尽力删除上次残留的 .part
→ 同一缓存键只选择最新的完整文件，尽力删除多余旧副本
→ 若总量超过启动保留目标，按下载完成时间从旧到新删除
→ 建立只存在于内存中的 key → 文件记录
→ 初始化完成，资源加载器开始工作
~~~

删除失败记录诊断并继续。没有降到目标容量也不阻止启动；无法创建或读取缓存根目录等基础故障才使初始化失败。不要持久化“待删除队列”，下一次应用启动重新扫描即可。

### 运行期取得文件

~~~text
加载器给出 FileRequest
→ 等待已显式启动的初始化完成
→ 查本地完整文件，按当前请求判断有效性
→ 有效：返回路径
→ 无有效文件：加入同 key 的共享下载，或启动一次下载
→ 写独立 .part，完成校验并关闭写入流
→ 改名为新的完整文件，更新内存记录
→ 返回路径
~~~

没有“检查容量”“先淘汰”“登记文件持有”“归还文件”等运行期步骤。下载失败只处理该尝试拥有的临时文件，不清理其他缓存。

### 应用退出

~~~text
停止新资源请求，按原规则排空资源和 AB
→ FileCache 停止接收请求并取消、等待在途下载结束
→ 释放缓存自有的取消和并发控制对象，由装配根释放网络传输
→ 已完成文件保留到下次启动
~~~

FileCache 关闭不等待资源引用或文件路径使用者，也不删除已发布文件。资源管理器的关闭规则不因此放宽。

## 3 保留和删除的职责

| 当前内容 | 处理 |
|---|---|
| FileCache 类型 | 保留名字以减少接入变化，内部按本文重写；不能仅关闭几个开关后留下旧体系 |
| FileIdentity、FileKeyEncoding | 保留现有稳定身份和无歧义哈希；不必为删减再发明一套地址系统 |
| FileRequest、FileValidity、TransportContext | 保留身份、来源、有效性、请求头及可选内容校验描述 |
| IFileTransport、TransportResponse、HttpFileTransport | 保留 HTTP 流式读取、超时、状态码与网络错误映射 |
| NetworkOptions | 保留下载并发、超时、重试设置；它们属于下载行为 |
| FileLease、PinCount、ReleaseLease | 删除，取得文件改为返回路径 |
| FileEntry 的 Ready/Retired/Deleting/Garbage 状态 | 删除，只保留普通文件记录 |
| DownloadJob/FileWaiter 及最后等待者取消状态机 | 删除，使用同 key 的共享 Task；新取消语义见第 6 节 |
| AccountedBytes/ReservedBytes、EnsureReservationAsync | 删除，运行期不记容量账、不逐块申请空间 |
| 元数据文件、MetaSchema、序列化和提交事务 | 删除，不写 .meta 或持久索引 |
| 访问时间刷写、精确 LRU、淘汰重试调度 | 删除，启动清理按下载完成时间排序 |
| generation 计数器和重启恢复代次 | 删除，唯一文件名即可；保留旧路径无须“退休”状态 |
| TrimAsync、Invalidate、运行期 ClearDiskCache | 删除，不提供绕过启动边界的删除入口 |
| FileCacheSnapshot、FileRow、TrimResult | 删除重型公开诊断模型；启动日志和下载错误已经足够 |
| 根目录文件锁和多实例协调 | 删除；装配根负责一个应用级实例、一个专用目录 |
| DownloadToAsync | 从 FileCache 移除，业务导出不进入本次缓存职责 |
| IFileCacheFileSystem、PhysicalFileCacheFileSystem | 删除公开文件系统抽象，直接使用 System.IO；保留必要的现有读取/错误辅助方法 |

不要求删除文件请求 DTO 中每一个字段来追求行数。要删除的是不再需要的运行机制和维护责任。

## 4 最小接口与配置

对外使用下面的接口形态，不再为一次文件使用分配可释放凭证：

~~~csharp
public sealed class FileCache
{
    public FileCache(FileCacheOptions options,
                     IFileTransport transport,
                     NetworkOptions network = null,
                     IResourceDiagnostics diagnostics = null);

    public Task InitializeAsync(CancellationToken cancellationToken = default);

    // 返回已完成文件的绝对路径；调用者不释放、不删除该文件。
    public Task<string> GetFileAsync(
        FileRequest request,
        CancellationToken cancellationToken = default);

    public Task ShutdownAsync(CancellationToken cancellationToken = default);
}

public sealed class FileCacheOptions
{
    public string Directory { get; set; }
    public long? StartupTargetBytes { get; set; } = 512L * 1024 * 1024;
}
~~~

- Directory 必须为专用缓存根目录；内部使用固定版本子目录，例如 http-cache-v2，不规定项目资源目录。
- StartupTargetBytes 为启动保留目标。null 表示不按总量删除；0 表示启动时尽力删掉全部完整缓存；负数非法。清理残留 .part 和同 key 多余旧副本不受该开关影响。
- 从现有 MaxBytes 迁移到 StartupTargetBytes；删除 TrimToRatio、MetadataAllowanceBytes、ResolvePath 及作为容量机制的 ChunkBytes。流式复制使用一个普通内部缓冲区即可。
- 已有 FileValidity 与远端加载器默认 TTL 保留；不要把 StartupTargetBytes 当成下载准入条件，也不要把启动清理规则当成内容有效性。
- 配置在构造时验证和复制，运行期间不读取外部可变配置对象。
- 保留现有诊断接口，使用已实现的安全分发方式。不要新建缓存专用日志框架。

FileCache 必须由应用装配根持有并注入远端加载器和内置 AB 加载器。同一实例重复 InitializeAsync 只等待同一个初始化任务；GetFileAsync 不能偷偷触发首次清理。未调用初始化时明确报初始化顺序错误；初始化已经开始时，可以等待其完成。

同一目录不支持并行的多个缓存实例或进程。这个限制作为装配契约，不通过文件锁、静态服务注册中心或跨进程协议实现。重建 ResourceManager 时继续使用原 FileCache。

## 5 文件格式与本地命中

### 用文件名恢复必要信息

采用一种固定且可校验的命名，例如：

~~~text
<Directory>/http-cache-v2/
    <keyHash>_<completedUtcTicks>_<randomId>.cache
    <randomId>.part
~~~

keyHash 继续使用 FileKeyEncoding.Encode(FileIdentity)。randomId 使用 GUID 等足够唯一的标识，文件以不覆盖已有路径的方式创建。completedUtcTicks 在下载完成并校验通过时确定；不要把读取文件的时间写回这个字段。

每个完整文件自带缓存键和下载完成时间；大小从文件系统读取。初始化扫描后建立普通字典，按同 key 最新完成文件恢复。不需要 .meta、索引文件、访问时间刷盘或两阶段数据/元数据提交。

只有本组件格式的 .cache 和 .part 是受管文件。扫描、删除都限定在该版本子目录，拒绝路径逃逸；未知文件或目录不自动删除，不跟随链接进入其他目录。文件名无法识别时记录并跳过，不把它交付为缓存命中。

一个普通内部记录已经足够：

~~~text
CachedRecord:
    Path
    CompletedAtUtc
    Length
    可选的已计算摘要（仅内存）
~~~

它不含 Pin、Generation、Retired、DeleteRetryAt 等字段，不要求成为公共类型。

### 命中和过期

- Immutable：调用方承诺身份对应内容不变，完整文件存在且满足请求校验即可使用。
- ExpiresAfter：用下载完成时间和本次 FileRequest 的 TTL 判断，命中时不延长 TTL。
- 缺文件、到期或校验不符：停止复用这个内存记录；旧完整文件留在磁盘，随后下载到新路径。
- 新下载失败：返回实际错误，不默认把过期文件当成功结果。
- FileCache TTL 不强制刷新 ResourceStore 已有的内存资源。这一点与现有资源共享规则一致。

同一身份不能表示不同内容。默认 URL 身份继续保留内容相关的端口和查询参数；只有加载器给出稳定业务身份时，才允许不同签名 URL 共用文件。解码器和表示参数仍影响内存资源身份，不能因此拆成多份相同下载文件。

保留 ExpectedLength、ExpectedSha256 校验，但不持久化校验索引：下载发布前校验已有声明；缓存命中和共享任务交付前满足当前调用者声明，必要时读取文件计算摘要。不能因为首个请求没有摘要，就忽略后来请求的摘要。已知相互冲突的声明应报身份冲突，不引入复杂的校验约束合并体系。

普通解码失败不自动证明下载文件损坏。不要顺便增加“解码失败就删除文件”、持久失效标记或自动无限重下。

## 6 并发与取消采用更简单的规则

### 共享下载

内部只需要一个 key → 共享 Task 的表。登记任务、查询文件记录、更新字典使用短同步临界区，网络与文件复制在外执行。先登记共享任务，再启动底层操作，防止同步完成时漏记或覆盖。

同 key 的请求等待同一次结果；不同 key 的下载受现有 NetworkOptions.MaxConcurrentDownloads 限制。任务真正结束后才移除记录，并确认移除的仍是本次记录。保留一小段任务和字典协调代码即可，不建立通用异步作业框架。

KeyedAsyncLock 可以用于确实需要串行的局部步骤，但不能把“依次拿锁”当成“共享同一次失败”。本次也不要求改造 AsyncLockSystem；无需在短同步字典操作外再叠加按键异步锁。

### 明确放宽文件层的取消语义

**调用者取消只停止自己的等待。即使所有调用者都取消，已启动或已排队的共享下载仍可完成并留作缓存。** 底层任务使用缓存自身生命周期令牌，不使用首个调用者的令牌。这条规则替代旧文件层“最后等待者离开就放弃下载”的契约。

这样不需要 FileWaiter 列表、等待者数量、Abandoning/Draining 状态和零接收者文件回收。代价是取消后可能仍有一次下载继续完成，这是本方案为减少复杂度明确接受的行为。

共享任务的异常即使无人等待也要被执行方观察；最终故障按现有诊断规则报告，不向已取消的业务调用者发送过期结果。下载仍受已有超时、有限重试和并发限制。

这次放宽只发生在下载缓存层。ResourceStore、实例池、AB 容器的独立等待者、共享所有权和取消规则仍按现有设计执行。

### 初始化和关闭

- 初始化只有一个共享任务；取消 InitializeAsync 的等待不撤销已经开始的初始化。初始化失败不开放 GetFileAsync，也不在运行期自动重试清理。
- ShutdownAsync 只有一个独立执行的关闭任务；每次调用均等待同一过程，调用者令牌只取消自己的等待。
- 关闭开始后拒绝新 Get；通过缓存自己的令牌取消在途/排队下载，并等真实任务收尾。不要因某个等待者先结束就提前释放传输对象。
- 关闭不等待文件使用者，不删除 .cache，不为了达到启动目标执行最后一次 Trim。
- 从未初始化就关闭时直接结束，不触发初始化或清理；初始化尚未完成时，由缓存自身的关闭令牌停止初始化并等待其收尾，不能随后重新开放 Get。关闭后不再接受 InitializeAsync。
- 传输对象由装配根创建和拥有，FileCache 不释放注入的 transport；装配根在缓存关闭完成后释放它。调用者取消关闭等待时，也不能提前释放 transport。

## 7 关键逻辑伪代码

以下是流程约束，不要求逐行照抄或一段伪代码对应一个类。

### 启动清理

~~~text
InitializeCore():
    创建专用版本子目录
    枚举本组件格式的文件
    尽力删除残留 part
    对完整文件按 key 分组：
        选下载完成时间最新的一份作为候选
        其余旧副本尝试删除
    统计仍存在的受管文件大小
    若设定 StartupTargetBytes 且仍超出：
        按完成时间从旧到新尝试删除完整文件
        删除成功才减少此次扫描的本地统计值
        删除失败记录并继续尝试其他文件
    从实际仍存在的候选文件建立内存字典
    标记初始化完成
~~~

扫描过程中的总量是一次清理使用的局部变量，不保留为运行期容量账本。即使部分删除失败，初始化结束后也不安排后台补删。

### 取得文件

~~~text
GetFileAsync(request, callerToken):
    验证请求与初始化顺序
    可取消地等待已存在的初始化任务
    检查缓存仍接受请求
    取得同 key 的本地记录
    如果存在且有效、满足本次校验：
        在交付边界检查 callerToken
        返回路径

    在短临界区内：
        重新检查关闭状态及是否已有新发布的记录
        若已有下载：取得它的 Task
        否则登记新的共享任务
    若本调用负责启动：在临界区外执行下载
    可取消地等待共享任务，不取消该 Task
    核验返回路径满足本次请求声明
    返回路径
~~~

校验需要 I/O 时在临界区外进行，更新记录时确认仍是原记录。重新查询发现新发布的有效记录就复用，避免两个同时未命中的调用在第一次下载完成后又启动第二次下载。

### 下载并发布

~~~text
DownloadAndPublish(request, cacheToken):
    try:
        等待下载并发槽位
        在有限重试次数内：
            try:
                创建本次尝试独占的 part 路径
                打开 HTTP 响应并流式写入 part
                校验长度及调用者提供的摘要
                完成写入并关闭文件句柄
                检查缓存生命周期令牌
                将 part 改名到从未使用过的完整文件路径
                更新 key 对应的内存记录
                完成共享任务并返回路径
            finally:
                关闭本次响应和写入流
                尽力删除本次尝试仍存在的 part
            可重试故障在该次清理完成后进入下一次尝试
    finally:
        若已取得并发槽位则释放
        按实际任务身份移除共享下载记录
~~~

每次尝试独立持有响应、流和临时文件；不能只在整个重试循环结束时清理最后一份 part。并发槽位和共享任务记录则由整个下载任务统一收尾。

只有明确瞬态网络错误可以重试；磁盘满、权限、校验失败沿现有错误规则返回。不要因为资源来源是 HTTP，就把本地写盘错误归为网络错误。

完整文件改名发布是路径可见性的分界。发布前失败的候选临时文件可以删除；发布后即使取消或后续内存记账失败，也不回删已完成文件，留给下次启动扫描。所有路径必须完成共享任务的成功、取消或失败信号，不能提前 return 后遗留等待者。

4. 文件本次运行不会被缓存组件删除，因此“不知道解码器是否仍读文件”不再需要文件隔离租约；这不代表可以忽略解码器自身的对象泄漏。
5. 保留已经修好的 URL 身份、默认有效期、FileLoadParameters、decoderId/DecodeKey 和错误传播，不能回退成旧版忽略参数或剥离查询的行为。

## 9 旧缓存迁移

新格式使用独立版本子目录，不读取或迁移旧 .meta、旧索引和旧租约。允许第一次升级后重新下载缓存，避免长期维护两套格式。

应用启动前，对确认属于旧 FileCache 的专用目录做一次性尽力清理；不能仅凭 data/meta/staging 等名字就删除整个 persistentDataPath 中的同名目录。旧 ResolvePath 曾把数据放到自定义路径时，由装配根提供确认过归属的清理位置；无法确认归属的内容不自动删除。

旧格式清理始终排除 http-cache-v2。新格式启用后，不得递归删除包含新格式目录的父目录；后续启动重试只处理已确认的旧文件或旧专用子目录。

新缓存启用前，旧缓存实例不能仍在运行。迁移删除失败记录诊断，下次应用启动再尝试；不增加运行期迁移服务。首次下载增加的 CDN 请求是格式切换的一次性成本，后续启动继续复用新格式完整文件。
